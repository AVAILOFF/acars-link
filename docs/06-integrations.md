## Hoppie ACARS

Checked against `https://www.hoppie.nl/acars/system/tech.html` on 2026-10-08 (T09). Implementation: `packages/transport/src/hoppie/`.

- Endpoint: `https://www.hoppie.nl/acars/system/connect.html` — **https works** (checked with a request, response `error {invalid logon code}`). The documentation shows only http and says "subject to change". We use https; the transport does not accept http.
- Parameters: `logon` (personal code, ≥ 24 characters for storage), `from`, `to`, `type`, `packet`. For server types (`poll`, `ping`) `to` is ignored but required — we send `SERVER`.
- Types: `ping` (connectivity check, does not mark the station online; `packet` holds a list of callsigns → the reply says who is online), `telex`, `poll`, `peek` (loggers only), `cpdlc`, `progress`, `position`, `posreq`, `datareq`; `inforeq` (metar/taf/…) is described but is not in the list of types. T09 uses `telex`, `poll` (and `ping` in the protocol).
- Code check (T56 U-06): tech.html recommends "a single ping" to test connectivity; it does not say that ping answers a wrong code. Checked on 2026-10-22 with a single GET `type=ping` with a deliberately wrong `logon`: the response was `error {invalid logon code}`. The response to a correct code (`ok`) is per the documentation; human check in T56.
- Response: `ok`, `ok {…}` or `error {reason}`. Poll: `ok {FROM type {packet}} {FROM type {packet}} …`; ping with callsigns: `ok {CS1 CS2}`. The documentation has **no** formal grammar — parsing is based on server responses and the open client `hoppie-connector` (Python); tests in `packages/transport/test/protocol.test.ts`.
- **GET and POST** are supported and can be mixed ("You may use either the GET or the POST protocol, or both intermixed", tech.html). **All requests are POST** (T68, 2026-10-29): `connect.html` has no URL parameters; `logon`, `from`, `to`, `type`, `packet` go in the `application/x-www-form-urlencoded` body so that the logon code does not end up in the URL (logs of proxies and of antivirus with HTTPS inspection, error texts). The server reads `logon` from the body — checked on 2026-10-29 with two `ping` requests by POST: without `logon` — `error (no logon code)`, with a wrong one — `error {invalid logon code}`. The response to a correct code by POST is a human check (T68).
- There is **no** hard limit on telex length; "kilobytes — unrealistic". The limit is set by the display profile.
- **Etiquette** (in the transport, invariant 6): poll every **45–75 s at random**; after a request that awaits a reply, poll at ~**20 s** for a short time (for us ≤ 3 min, `expectReply`); **do not start polling until the station has sent its first message**; HTTP timeout **15 s**; on a poll timeout, skip to the next interval; retry a send after a few seconds (our backoff is 5 s × 2ⁿ ± 20 %, ≤ 5 min, 6 attempts); do not send many messages within 2 s (we keep ≥ 2 s between any requests, one request in flight).
- **Callsign lock:** on the triple (logon, network, callsign); set by every request except `peek`/`ping`; TTL **100 s**, extended by any action. One logon can hold several callsigns. A conflict gives `callsign already in use` (retry after 110 s). So the **lock applies to the telex `from`** — the station `OPS{flight}` is locked to the pilot's code while the flight is in progress.
- A wrong code → `error {invalid logon code}` / `illegal logon code` → the transport goes to `halted`, the queue is kept.
- The documentation does not define the callsign format; we accept `A–Z0–9`, 2–16 characters; the maximum length is `[VERIFY]` (`OPSDLH123` is 9).

## CPDLC over Hoppie (T23)

Checked 2026-10-09. Hoppie does not parse CPDLC: it is free text in a `cpdlc` message, handled by clients (tech.html: "@" — line breaks for display). The packet format and phrases come from open code and captured packets. No code was copied, only the format was taken.
- Sources: FlyByWire A32NX `fbw-common/src/systems/datalink` (`AcarsConnector.ts`, `CpdlcMessage.ts`, `CpdlcMessageElements.ts`, `ATC.ts`; GPL-3.0); network packets from YV E-Jet `Nasal/cpdlc/hoppie-driver.nas` and `hoppie-standalone` (MIT); the TopSky manual "Data Link Functions" v2.2 (2017); the Hoppie ACARS ATC Client page (`hoppie.nl/acars/prg/atc`).
- Packet: `/data2/<min>/<mrn>/<ra>/<text>`. `min` is the sender's counter, `mrn` is the `min` of the message being replied to (empty in the first one), `ra` is `WU`, `AN`, `R`, `NE`, `Y`, `N`. FBW takes the text as the sixth field of `split('/')`, so an uplink text contains no `/`. `@` marks a value, `@_@` separates parts of a line.
- Logon: the aircraft sends `/data2/n//Y/REQUEST LOGON` (this is what the A350/A380 send, T09). The station replies `/data2/m/n/NE/LOGON ACCEPTED` and `CURRENT ATC UNIT@_@EDGG@_@LANGEN CTL` (oceanic — `… OCA`). A refusal is `UNABLE …` (FBW: UM9996/UM0). Handover: `HANDOVER @EDUU` (NE) — FBW sends LOGOFF to the old station and REQUEST LOGON to the new one. End of contact — `LOGOFF` (NE).
- Callsigns of live stations are 4 characters (TopSky: "four characters"): EDGG, EDYJ, LONC, EUWN. XATC uses `X` + FIR (decision 2026-10-09, `07` T23).
- Polling: per tech.html, aircraft clients must wait for the first message; an ATC station waits for a logon, so it is polled from the start (the same 45–75 s; after HANDOVER — 20 s, for no longer than 3 min).
- `[VERIFY]` by a human: display in the PMDG 777/737 (737 MSFS 2024 — checklist in `07`, T52), Fenix, iniBuilds; auto-logon after HANDOVER on non-FBW aircraft.

## DCL/PDC over Hoppie (T24)

Checked 2026-10-09. Implementation: `packages/core/src/atc/dcl.ts`, decisions and assumptions: `07`, T24.
- Request (RCD) — a telex from the aircraft: `REQUEST PREDEP CLEARANCE` / `<callsign> <type> TO <dest.>` / `AT <departure> STAND <x>` / `ATIS <letter>` (FBW `DclMessage.ts`, GPL-3.0, format only; the TopSky example "ATIS PAPA" — the letter as a word).
- ARINC 623 DCL. Format sources: AIP Singapore eSUP 2018/013 (`aim-sg.caas.gov.sg`), AIP Malaysia SUP 02/25 (`aip.caam.gov.my`): RCD, FSM (`FSM hhmm yymmdd WSSS` / `SIA123 RCD RECEIVED` / `REQUEST BEING PROCESSED` / `STANDBY`; `RCD REJECTED` / `REVERT TO VOICE PROCEDURES`; `CDA RECEIVED` / `CLEARANCE CONFIRMED`), CLD (`CLD hhmm yymmdd WSSS PDC 001` / `SIA123 CLRD TO WMKK OFF 02C VIA MASBO2A` / `SQUAWK 2201` / `NEXT FREQ 121.65 ATIS B`), CDA, timings (CLD within 5 min, pilot reply within 5 min, a request no earlier than 20 min before TOBT). Real CLD messages from the ACARS air are test samples of `plane-watch/acars-parser` (`internal/parsers/pdc/*_test.go`, no license stated, only the format was taken) and `airframesio/acars-message-documentation` (`research/A3.md`): EDDF, EFHK, EGLL, EPWA, LSZH, VHHH, WSSS, VTBS, RKSI. On the Hoppie wire — as in TopSky (manual "Data Link Functions" v2.2 and captured network packets): `/data2/n//NE/FSM … @CS@ RCD RECEIVED @REQUEST BEING PROCESSED @STANDBY`, `/data2/n//WU/CLD … PDC nnn @CS@ CLRD TO @DEST@ OFF @RWY@ VIA @SID@ SQUAWK @XXXX@ …`, pilot reply `/data2/m/n/N/WILCO`.
- USA: the PDC goes through the airline host, there is no pilot reply (TopSky 1.4; FAA JO 7110.113F, 2017-10-02: fields SID, Transition, Climb Out, CLIMB VIA, Maintain, Expected Altitude, Departure Frequency, Contact, Local Info; "Cleared as filed" is not used in the ATC fields). The layout is a real Delta PDC DAL2699 KMSP–KRDU of 2025-12-29 (`plane-watch/acars-parser`).
- `[VERIFY]` by a human: which aircraft accept DCL/PDC (FBW — the DEPART REQ page; PMDG, Fenix, iniBuilds), display of WU buttons on a CLD.

## NAT oceanic clearance (T27)

Checked 2026-10-09.
- **Status in the NAT.** NAT OPS Bulletin 2023_001 rev 6 (ICAO EUR/NAT, 25 Feb 2026): clearances are withdrawn (Oceanic Clearance Removal) everywhere except **Shanwick**, which issues a clearance after an RCL "until further notice" (the transition date is by NOTAM). The RCL is sent to Bodø, Gander, Santa Maria, Shanwick; New York East and Reykjavik do not require it (Reykjavik replies that no RCL is needed). The reply of areas without a clearance is `RCL RECEIVED BY [ANSP]` (the exact word after BY is known only from a comment on ops.group: "RCL received by Santa Maria"). RCL windows before the entry point: Gander 90–60 min, Shanwick 90–30, Santa Maria ≥ 40, Bodø ≥ 20. The RCL contains: OEP, ETO, Mach, level, `MAX FL` as free text (without MAX, the requested level is taken as the highest).
- **CLX format and errors.** NAT OPS Bulletin 2020_001 rev 01 (14 Jun 2022), §4–12: `CLX hhmm yymmdd EGGX CLRNCE nnn` / `<callsign> CLRD TO <dest.> VIA <OEP>` / `NAT <letter>` or `RANDOM ROUTE` / points / `FM <OEP>/<ETO> MNTN F<level> M<mach>` / `ATC/ …` (LEVEL CHANGE, MACH CHANGE, ENTRY POINT CHANGE, ROUTE CHANGE, RECLEARANCE n) / `END OF MESSAGE`. The Shanwick example in §12: a route without repeating the OEP, up to the exit point. Messages: `RCL RECEIVED` + `IF NO CLEARANCE WITHIN 15 MINUTES CONTACT SHANWICK BY VOICE`; `RCL REJECTED` + `RCL SENT TOO EARLY` / `RCL RECEIVED TOO LATE REVERT TO VOICE PROCEDURES` / `REQUEST BEING PROCESSED AWAIT TRANSACTION COMPLETION` / `FLIGHT PLAN NOT HELD` / `INVALID <…> RESUBMIT YOUR REQUEST`; `RCL/CLA RECEIVED NEGOTIATION REQUIRED CONTACT SHANWICK BY VOICE`; `CLA RECEIVED CLEARANCE CONFIRMED END OF MESSAGE`; without a CLA for 10 min — `CLEARANCE CANCELLED REVERT TO VOICE PROCEDURES` (§7.1, Shanwick). The level in a CLX is not a clearance to climb (§5.3). Coordinates are as in the FPL (Doc 4444, App. 2, field 15): `57N020W`, with minutes `5530N02000W`.
- **Hoppie.** FlyByWire `OclMessage.ts` (GPL-3.0, format only): RCL — a `cpdlc` packet `/data2/<min>//N/OCEANIC REQUEST
<callsign> 
ENTRY POINT:<OEP>
AT:<hhmm>Z 
REQ:M.<mach> FL<level>[
<free text>]` to the station the aircraft is logged on to (`atsu.currentStation()`). `ATS623.ts`: the reply is accepted from the same station, a telex turns into free text UM169 awaiting ROGER; a reply with `TO <destination>` closes the exchange. Which other aircraft send an RCL through Hoppie — `[VERIFY]` by a human.
- **Tracks.** natTrak (VATSIM, `https://nattrak.vatsim.net/api/tracks`): `[{identifier, active, last_routeing: "SUNOT 58/20 60/30 60/40 59/50 AVUTI", valid_from, valid_to, concorde, flight_levels: [34000, …], direction}]`, the data comes from the real NAT track NOTAMs (`TracksService.php`). Active tracks only. The license of the code and the API terms are not published — `[AT RELEASE]`. FAA `notams.faa.gov/common/nat.html` did not open from the network (403), FlightPlanDatabase `/nav/NATS` returned an empty list. The SimBrief OFP has a `tracks` field (empty for RCTP–RJBB) — the format on a real transatlantic OFP is `[AT RELEASE]`. **T72 (decision 2026-10-31):** natTrak is only in the personal build (a fallback source); in the public build the adapter is replaced by an empty one (`apps/desktop/variants/public/nattrak.ts`), tracks come from the `tracks` field of the SimBrief OFP. The format of `tracks` is documented nowhere (Navigraph, the `SimbriefOfp` interface in MSFS avionics, GitHub search, 2026-10-31), so it was taken from a real KATL–EDDF OFP (2026-10-31, `json=v2`): `tracks: { nat_notams: { eggx, czqx }, nat: [...] }`; `nat_notams` is the raw text of the track NOTAMs for Shanwick and Gander (we do not parse it); `nat` is all 12 tracks for the day (A–F `group: West`, `addr: EGGX`; U–Z `group: East`, `addr: CZQX`), each with `id`, `group`, `addr`, `tmi`, `route` (`SUPRY 46N050W 49N040W 51N030W 52N020W LIMRI XETBO`, coordinates in flight-plan form), `levels` (`340 350 …`, flight levels), `start` / `end` (UTC `YYYY-MM-DDTHH:MM:SSZ`), `fixes[]` (`ident`, `pos_lat`, `pos_long`). In `json=1` the same fields differ (`start` / `end` in unix seconds, `fixes.fix`, `nat` is an object with keys 0…11); the application requests `json=v2`. The aircraft's track in the navlog is marked `via_airway: NATW`. Parsing: `packages/core/src/ofp/parse.ts` (`Ofp.natTracks`: the route in the form of a track message `58/20`, levels in feet, validity in ms); a track that cannot be read is skipped, the OFP is not rejected. Not checked on a live OFP: half-degree latitudes (`5530N02000W`) and a single track (an object without an array) — parsing follows the flight-plan rules, tests on synthetic data `[VERIFY]`. For an eastbound flight (Gander) there is no clearance: the track in the CLX is needed only for Shanwick, i.e. on a westbound flight (A–F).
- **Areas.** The first oceanic area after the OEP — by the SimBrief `fir` of the first coordinate point, otherwise by VATSpy: EGGX, CZQX/CZQO (Gander), BIRD, ENOB, LPPO, KZWY/KZNY. The VATSpy `oceanic` flag is unreliable (it is `0` for EGGX and CZQO). The SimBrief `fir` codes of oceanic points on a real OFP are `[AT RELEASE]`.

## OpenFlights (T43)

- Data: `airlines.dat`, `airports.dat`, `routes.dat` from github.com/jpatokal/openflights (`data/`, last changed 2017-02-02), description — openflights.org/data.php (checked 2026-10-15). The table in the core `packages/core/src/ext/openflights.ts` is generated by `node tools/openflights/generate.mjs <folder> packages/core/src/ext/openflights.ts`; do not edit by hand.
- **License:** the databases are under the Open Database License (ODbL), the contents under the Database Contents License; route data (Airline Route Mapper) is public domain; airline data from Wikipedia may be under the GFDL. Requirements: credit the source (OpenFlights.org); derived databases published openly must also be under a free license (our table is ODbL); commercial use requires a separate OpenFlights license. User decision 2026-10-15: use it (item 12 of T43). `[AT RELEASE]` — credit the source in "About".
- **Freshness:** routes have not been updated since June 2014 ("historical interest only"), the airline `active` flag is unreliable. So from the routes we take only "the airline operated its own (non-codeshare) departures from the airport" — without flight numbers, destinations or times.
- Routes: `routes.dat` by `airline id` → the airline's ICAO (`airlines.dat`), by `source airport id` → the airport's ICAO (`airports.dat`); rows without ICAO codes are dropped (470 airlines, ~14.8 thousand pairs). The airline's country is the `country` field of active records; an ICAO code shared by active airlines of different countries is not taken.
- **T53 (user decision 2026-10-15):** also `planes.dat` (the same repository and license; ICAO type → IATA code). An airline's hub is the airport with the largest number of its own direct routes (`stops` = 0, a known destination airport); a tie for first place means no hub (405 hubs). For a hub the route destinations and aircraft types are kept (the `equipment` field, IATA codes): after a flight to the hub, the next flight goes to one of them, only if the flight's aircraft type flew on that route. The flight number is still not taken from OpenFlights (it is not there). The data was downloaded and checked on 2026-10-15; the table of the earlier fields did not change on regeneration.

## SimBrief

- `https://www.simbrief.com/api/xml.fetcher.php?userid=<pilot id>&json=v2` (or `username=`). **The format is `json=v2`** (decision 2026-10-08, Navigraph's recommendation for new projects). `json=v2:1` is not supported.
- Checked on a real OFP (2026-10-08). Features of `json=v2`:
  - all values are **strings**, including numbers (`"182664"`, `".84"`); an empty value is `""`;
  - times are ISO UTC (`"2026-10-08T07:45:00Z"`), durations are `"HH:MM:SS"`;
  - lists are always arrays: `alternate[]`, `navlog[]` (without the `fix` wrapper), `origin.atis[]`;
  - `params.units` is `"kgs"` or `"lbs"`; weights and fuel are in these units, counts (`pax_count`) are not;
  - `navlog[].distance` is the leg length (the sum = `general.route_distance`); TOC/TOD — `ident: "TOC"/"TOD"`, `type: "ltlg"`; `stage` — `CLB/CRZ/DSC`;
  - `aircraft.equip_category` is the wake turbulence category (`H` and so on).
- **TLR and crew (T43, checked on a real A35K RCTP–RJBB OFP 2026-10-08, re-checked 2026-10-15).** `tlr.takeoff.conditions.planned_runway` and `tlr.takeoff.runway[]` (one entry per runway): `identifier`, `flap_setting`, `thrust_setting` (`FLEX`), `flex_temperature` (°C), `speeds_v1/vr/v2` (kt); `tlr.landing.conditions` (`planned_runway`, `flap_setting`, `surface_condition` `dry`/`wet`), `tlr.landing.distance_dry|distance_wet.speeds_vref`. `crew`: `cpt`, `fo`, `dx` (dispatcher, not on board), `pu`, `fa[]` — names (`cpt` is the pilot's name). We take only the planned runway numbers and the crew headcount; names are not used. The `tlr` section is absent if the OFP was built without TLR. The fields are not described in the public SimBrief documentation. `thrust_setting`/`flex_temperature` on Boeing (D-TO, assumed temperature) — `[VERIFY]` on a real OFP; a single runway in `runway` as an object rather than an array is an assumption, the parser accepts both forms.
- **ETOPS (T50, checked on a real A35K RJTT–KLAX OFP, rule 370, 2026-10-15).** `etops` is an object: `rule` (min), `entry` / `exit` (`icao_code`, `pos_lat_apt` / `pos_long_apt` — the entry/exit airport, `pos_lat_fix` / `pos_long_fix` — the point, `elapsed_time`, `min_fob`, `div_time`, `div_burn`, `critical_fuel`, `div_airport{icao_code, distance, …}`), `suitable_airport[]` (fields as for `alternate`: `icao_code`, `name`, `pos_lat`, `pos_long`, `elevation`, `plan_rwy`… plus the window `suitability_start` / `suitability_end`, `metar`, `taf`, `notam[]`), `equal_time_point[]` (`pos_lat`, `pos_long`, `div_airport[]`), `critical_point` (`fix_type: ETP`, coordinates). Without ETOPS — `etops: []`. We take the rule, entry, exit and suitable airports (diversion candidates). `enroute_altn` (ERA) and `takeoff_altn` are empty arrays in this OFP: the structure of the elements is `[VERIFY]` on an OFP with ERA and a takeoff alternate. The fields are not described in the public SimBrief documentation (there are only the request parameters `etops`, `etopsrule`, `etopsentry`, `etopsexit`, `etopsaltn1…`).
- **NOTAM (T95, checked on 4 OFPs from `reference/ofp/raw`, 400 entries, 2026-11-07).** `origin`, `destination`, `alternate` (and `etops.suitable_airport`) have a `notam[]` array: `notam_id`, `location_icao`, `date_effective` (UTC `YYYY-MM-DDTHH:MM:SSZ`), `date_expire` (the same or `false` — `C) PERM`), `date_expire_is_estimated` (`true`/`false`, `"1"` or `{}` — different types in one OFP), `notam_schedule` (field D as text, `""` or `{}`), `notam_text` (field E; if there is a schedule, SimBrief puts it on the first line), `notam_raw`, `notam_html`, `notam_qcode` (`QMRLC`; for domestic US NOTAMs and some others — `[]`, 22 of 400), `notam_qcode_*`, `notam_is_obstacle`. The fields are not described in the public SimBrief documentation. Parsing: `parse.ts` (`Ofp.notams`, without `raw`/`html`); an entry that cannot be read is skipped, the OFP is not rejected. Decoding of Q-codes — FAA JO 7930.2U, appendix B (public domain, 2026-11-07); selection for the summary — `packages/core/src/ext/notam.ts`. The test fixture `packages/core/test/fixtures/ofp/notams-rjbb-rjgg.json` has only the NOTAM fields, no pilot data.
- Fields and their mapping — `packages/core/src/ofp/` (the `Ofp` type, `parseSimbriefOfp`). Format errors — `OfpParseError` with the field path.
- Test samples are made by `tools/anonymize-ofp.mjs` from raw OFPs in `reference/ofp/raw/` (in `.gitignore`). Do not commit raw OFPs: they contain the pilot id and names.

## GSX VDGS (T22)

- Source: FSDreamTeam, "VGDS Custom Messages System — Developer Manual", 2025-07-29. It ships with GSX Pro: `<Addon Manager>\couatl\GSX\SDK\Samples\VGDS\vgds_developer_manual.pdf`, next to it sample `*.json` files and the editor `GSX\VGDSEditor`. - Second source (checked 2026-11-05): FSDreamTeam, "VGDS Message Editor User Manual", shipped with GSX Pro (`<Addon Manager>\couatl\VGDS_EDITOR_USER_MANUAL.pdf`, file of 2025-08-01). The last line of narrow, wide and x ("Reserved Lines") is taken by the GSX scrolling line; for our own text — narrow 5, wide 6, x 6 lines; for small — lines 1–2. The developer manual also allows filling everything ("Advanced: last physical line is used/cleared"), but then the GSX line is overwritten — we do not touch it. Also there: custom messages go after the standard GSX messages and repeat in a loop while the aircraft is at the stand; the `flex` type (SafeDock FLEX, 10 characters, 6 lines, of which 5 are ours) is in the editor and in the standard `flight_information`; we write it since 2026-11-05 (at a FLEX stand, EDDF A19, without a `flex` variant GSX showed its own message), without own `flex` lines `flex` takes `narrow`; the character set is ASCII (letters of both cases, digits, a few signs), ours is within it.
- Not described or differs from the manual `[VERIFY]` by a human in the simulator: when the custom message is shown relative to the parking guidance; what the board shows if there is no variant for its type (per the editor manual — the message is not shown). The examples and the standard file have the colour `green` and the field `data_source` — they are not in the manuals, we do not use them; `overrides` (replacing a standard message, for example `chock_and_gate_display`) are described in the editor manual; T102 replaces `flight_information`: a message with the same `id` **and** the file field `"overrides": { "stock": ["flight_information"] }` (sample `SDK\Samples\VGDS\sample_chock_override.json`, the editor manual — "Override System", "Override and Filtering Interaction"; checked 2026-11-05). ### Implementation (T13)

The package `packages/data-sources` (`@acars/data-sources`): parsers, `ExternalDataService` (schedule, cache, degradation), no Node API (HTTP through an `HttpClient` of the same shape as in the transport). Responses were checked with requests on 2026-10-08; trimmed fixtures — `packages/data-sources/test/fixtures/` (VATSIM — without names and CIDs, the stations EDDF/KJFK/RJBB are synthetic).

- **aviationweather.gov**: `GET https://aviationweather.gov/api/data/metar?ids=A,B&format=json` → `[{icaoId, obsTime (epoch s), rawOb, …}]`; `…/taf?…` → `[{icaoId, rawTAF, mostRecent, …}]`; **204** — no data. The limit is **100 requests/min**, a custom User-Agent is requested; METAR usually once an hour, TAF once every few hours. From `rawOb` we strip `METAR `/`SPECI ` and the `$` flag (the formatter would turn it into `USD`).
- **VATSIM**: the feed URL comes from `https://status.vatsim.net/status.json` → `https://data.vatsim.net/v3/vatsim-data.json` (~1.5 MB, updated every 15 s). `controllers[]`/`atis[]`: `callsign`, `frequency`, `facility` (0 OBS, 1 FSS, 2 DEL, 3 GND, 4 TWR, 5 APP, 6 CTR), `atis_code`. The station's airport is by the callsign prefix: ICAO, IATA, for `K…` the ICAO without `K` (`MCI_TWR`) `[VERIFY]` other local conventions. The formatter shows `_` in callsigns as `-`.

### FIR boundaries (T23)

- **VATSpy Data Project** (`github.com/vatsimnetwork/vatspy-data-project`), license **CC BY-SA 4.0**, checked 2026-10-09 (release v2610.1). Files: `https://raw.githubusercontent.com/vatsimnetwork/vatspy-data-project/master/Boundaries.geojson` (~2.2 MB) and `…/VATSpy.dat` (~0.9 MB).
- `Boundaries.geojson` is RFC 7946, each object has a MultiPolygon and properties `id` (FIR `EDGG`, sector `EDGG-N`), `oceanic` (`"0"`/`"1"`), `label_lon`, `label_lat`, `region`, `division`. The polygons are cut along the antimeridian (there are no coordinates beyond ±180 and no spans larger than 180°). Some `id`s occur twice (`KZNY`: land and ocean) — they are merged. FIRs are only the 4-letter `id`s (approved, `07` T23). Among them are overlay areas without airports (`EGVV` Swanwick Military over Great Britain, `EDXX` FIS only over Germany) and sub-areas (`EGTL` London TMA inside `EGTT`). On an overlap, the areas that `[Airports]` names as the airport's FIR come first, then the larger one is taken. In Australia VATSpy has only sectors (`YGUN` and so on).
- `VATSpy.dat`: `[FIRs]` — rows `ICAO|NAME|CALLSIGN PREFIX|FIR BOUNDARY` (an empty prefix = ICAO), `[UIRs]` — `ID|NAME|FIR,FIR,…` (there are sectors `EDGG-BAD`), `[Airports]` — `ICAO|NAME|LAT|LON|IATA/LID|FIR|IsPseudo` (the airport's FIR per VATSIM, pseudo entries `IsPseudo=1` are not taken), `[Countries]` — `NAME|PREFIX|…`. From here come the names of the bodies and the FIRs of online VATSIM centres: the longest prefix from the parts of the callsign up to the suffix (`EDGG_DKB_CTR` → `EDGG_DKB` → EDGG, `LON_S_CTR` → `LON` → EGTT), a UIR — all its FIRs (`-` in the id → `_` in the callsign).
- Only the FIRs along the route (route points at ≤ 10 NM) and the centres covering them go into the core and the flight recording. VATSIM: CTR (facility 6) and FSS (1) on frequencies 118–137 MHz. Loading — once per flight with the station enabled, cache 7 days, after a failure — in 10 min, at most 3 attempts. Implementation: `packages/data-sources/src/vatspy.ts`, fixture — `packages/data-sources/test/fixtures/` (a trimmed real release, the same license).
