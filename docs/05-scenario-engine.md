# 05 — Движок сценариев

Сценарии описываются в YAML, валидируются JSON Schema, исполняются ядром детерминированно (seeded Rng). Примеры — `reference/scenarios/`.

## Модель

```yaml
id: string                 # уникальный, snake_case
version: 1
category: docs | ops | irregular | external | fun
title: string              # для UI настроек
enabled_by_default: bool
trigger:                   # когда сценарий становится кандидатом
  on: phase_enter | phase | event | time | distance
  phase: CRUISE            # для phase_enter / phase
  event: OOOI_OFF          # для event
  at: { rel: sched_out, offset_min: -25 }       # для time
  dist: { to: tod, lte_nm: 150 }                # для distance
conditions:                # все должны выполняться
  - "ofp.block_time_min >= 90"
  - "aircraft.cat in ['M','H']"
probability: 0.05          # 0..1, бросок один раз при входе в кандидаты
cooldown: per_flight | per_session | { minutes: 120 }
excludes: [other_scenario_id]   # взаимоисключение
group: special_news        # группа (T39): лимит max_per_flight — в packages/scenarios/src/groups.ts
priority: 0                # при конфликте на одном тике
steps:                     # последовательность
  - send: template_id | inline text
    vars: { ... }          # локальные переменные
  - wait: { minutes: 5 } | { phase: DESCENT } | { reply: { options: [CONTINUE, DIVERT], timeout_min: 10, default: CONTINUE } } | { until: "flight.dist_to_tod_nm < 80", timeout_min: 90 }
  - branch:
      DIVERT: [ { send: ... } ]
      CONTINUE: [ { send: ... } ]
  - set: { flags.mel_item: "21-31-01" }   # влияет на следующие сценарии и следующий рейс
```

## Шаблоны

- Синтаксис: `{var}`, `{var|fmt}`. Форматтеры: `kg1` (12345 → 12.3), `hhmm`, `ddmmm`, `pad:N`, `upper`, `qnh`.
- Генераторы: `{rand:10-35}`, `{pick:[A,B,C]}`, `{name:crew}` (по стране авиакомпании), `{seat}` (буквы по типу самолёта, T40; `{seat:1-2}` — только ряды 1–2, T41), `{hold}` (отсек: `FWD/AFT/BULK HOLD`, у широких + `LD3`/`PALLET`).
- Блоки шаблона: `header` / `body` / `footer`. Линии и разделители подставляет форматтер по `DisplayProfile`.
- Все переменные берутся из контекста: `ofp.*`, `tm.*` (телеметрия), `phase`, `flight.*` (OOOI, seed, флаги), `wx.*`, `ext.*`.

## Исполнение

1. На каждом тике ядро вычисляет набор кандидатов по `trigger` и `conditions`.
2. Для новых кандидатов: бросок `probability` (seeded). Проверка `cooldown`, `excludes` и лимита группы.
3. Активные сценарии исполняются как корутины по `steps`. `wait` переводит сценарий в ожидание события.
4. Исходящие сообщения → форматтер → очередь транспорта (rate limit).
5. Входящий telex от пилота сопоставляется с ожидающими `reply`. Если ожидающих нет — с глобальными «командами» (`REQ WX`, `REQ GATE`…).

## Входящие команды пилота (v1)

| Команда | Ответ |
|---|---|
| `REQ WX <ICAO>` | METAR/TAF |
| `REQ GATE` | назначенный гейт и стоянка |
| `REQ LOADSHEET` | повтор последнего лоадшита |
| `DELAY <мин> <причина>` | подтверждение, сдвиг расписания |
| `DIVERT <ICAO>` | цепочка диверсии |
| `ETA` | ETA и данные по стыковкам |

Парсер терпим к пробелам и регистру. Неизвестная команда → вежливый `UNABLE / SEND HELP FOR LIST`.

## Валидация контента

- JSON Schema + тест, который прогоняет каждый сценарий на 3 синтетических полётах и проверяет: шаблоны раскрываются, строки ≤ ширины профиля, нет запрещённых символов.
- LLM (опц.): шаг `send` может иметь `llm_flavor: true`. Тогда бэкенд перефразирует **только** свободный текст. Результат проходит те же проверки, при провале используется исходный шаблон.

## Реализация v0 (T06)

- Код: `packages/core/src/scenario/` (типы, условия, шаблоны, контекст, движок), `packages/core/src/core.ts` (`AcarsCore`: FSM + движок по контракту из `03`), `packages/scenarios/src/` (YAML 1.2 → JSON Schema → `compileScenario`).
- Триггеры: `phase_enter`, `phase`, `event` (события FSM, кроме `TELEMETRY_LOST`), `time` (`rel`: `sched_*`, `est_*`, фактические `out/off/on/in`), `distance` (`to: dest | tod | orig`, `lte_nm` / `gte_nm`). Шаги: `send`, `wait: { minutes }`, `wait: { phase }`; `reply`, `branch` — T12 (см. ниже), `set` — T14 (см. ниже).
- Кандидат = триггер **и** условия стали истинны на этом тике (фронт). Затем cooldown, лимит группы, `excludes` (в обе стороны), бросок `probability`; старт по `priority` (убыв.), затем по `id`.
- У каждого сценария свой Rng с seed `<seed>/<id>`: добавление сценария не меняет броски других.
- `wait.minutes` считает «время полёта» FSM (× `simRate`, без пауз); `time`-триггеры — по `Clock`. Пока телеметрия потеряна, движок стоит.
- Переменные — `CONTEXT_VARIABLES` в `scenario/context.ts` (`ofp.*`, `aircraft.*`, `tm.*`, `flight.*`, `phase`); неизвестная переменная — ошибка загрузки. Отсутствующее значение печатается как `----`.
- Форматтеры: `kg1`, `hhmm`, `ddmmm`, `pad:N`, `lpad:N`, `int`, `upper`, `qnh` (T13: группа `Q1013`/`A2992` из METAR). Генераторы: `rand`, `pick`, `seat`; `name:*` — T07.
- T07 добавил: форматтер `sign` (+3 / -120 / 0), генераторы `{name:crew}` / `{name:ops}`.
- **Поздний старт** (решение пользователя 2026-10-08, после проверки T10: при старте за 5 мин до STD пять предвылетных telex пришли разом и не по порядку). На первом тике движок считает задержку: если до `sched_out` осталось меньше `lateStartLeadMin` (по умолчанию 35 мин — столько длится посадка в синтетическом профиле), рейс считается задержанным на недостающее время, с округлением вверх до 5 мин. Триггеры `time` с `rel: sched_*` и `est_*`, переменные `ofp.est_*`, `ops.ctot`, `ops.next_std` сдвигаются на задержку; `ofp.sched_*` (STD/STA в текстах) — нет. Переменная `flight.delay_min` — задержка в минутах (0 — вовремя). Задержка — часть состояния движка (`delayMs`), один и тот же (OFP, запись, seed) даёт одну и ту же задержку. Сценарии, время которых для задержанного рейса уже прошло к старту (например, `crew_info` за 45 мин), уходят на первом тике. **Подгонка под оставшееся время** (решение пользователя 2026-10-18, `lateStartVersion: 2`; приложение включает её и пишет в заголовок записи, без неё — версия 1, как выше): задержка объявляется только при остатке меньше 20 мин. Если до STD осталось меньше, чем самый ранний триггер `sched_out − N` (сейчас 60 мин), смещения `sched_out − N` умножаются на `(остаток − 1 мин) / самое большое N` — например, за 30 или 50 мин до STD приходят все документы, в том же порядке и пропорциях, и все до STD. Коэффициент хранится в состоянии (`preScale`). **Только сценарии, которые могут сработать** (решение пользователя 2026-10-22, `lateStartVersion: 3`, приложение пишет её в заголовок записи): при старте за 27 мин до STD первый telex пришёл через 7,5 мин, потому что «самое большое N» давал `discretion_followup` (−60), которому нужен флаг прошлого рейса. В версии 3 самое большое N берётся на первом тике только среди сценариев, которые ещё могут начаться: не исключены условием на значения, известные при старте (`flags.*`, `ofp.*`, `phase`), кулдауном или первым броском вероятности (бросок подсматривается на копии Rng сценария, настоящий бросок тот же). Условия на живые данные (`tm.*`, `wx.*`, `ext.*` …) не исключают — они ещё могут стать истинными.

## Двусторонняя связь (T12)

- **Вход ядра** — `CoreInput.inbound: PilotMessage[]` (`{ from, type, text }`, контракт `03`). Приложение передаёт с ближайшим тиком: telex, полученные транспортом, и текст, набранный в окне «Ответить за пилота» (для самолётов без свободного telex — A350/A380, `06`; в сеть не уходит). Учитываются только `type: telex` от позывного рейса; CPDLC (логон A350/A380), чужие позывные и пустые сообщения — событие `PILOT_MESSAGE` с `result: ignored`. Пока телеметрия потеряна, сообщения ждут в состоянии ядра (`inbox`).
- **Нормализация**: верхний регистр, всё кроме `A–Z0–9` → пробел (`REQ-REFUEL` из Fenix, `req  wx/eddf`), `core/src/scenario/pilot.ts`.
- **`wait: { reply: { options, timeout_min, default } }`**: варианты — одно слово `A–Z0–9`, `default` обязателен и входит в `options`. Ответ — сообщение пилота, первое слово которого — вариант (при нескольких ожидающих — самый ранний запуск); остальные слова — `reply.arg`. Без ответа за `timeout_min` **полётного** времени (как `wait.minutes`: пауза не идёт, ×N ускоряет) берётся `default`, `reply.timeout = true`. Ответ на вопрос важнее команды с тем же словом (`DIVERT`). Событие `REPLY_EXPECTED` — приложение просит транспорт чаще опрашивать (`expectReply`, у Hoppie ≤ 3 мин), `REPLY_TIMEOUT` — в ленту.
- **`branch: { ВАРИАНТ: [шаги], … }`** — по последнему ответу (`reply.option`); ответ без ветки — дальше после `branch`. Ветки вложенные; ключи проверяются по ближайшему `wait: reply`; `branch` после ветвления, где ветки задавали разные вопросы, без нового вопроса — ошибка загрузки. Компилируется в плоскую программу с переходами — состояние прогона по-прежнему номер шага (сериализуется).
- **`wait: { until: "<условие>", timeout_min }`** (T39): условие — на языке `conditions`, проверяется при входе в шаг (уже истинно — ждать не нужно) и на каждом тике; пока телеметрия потеряна, не проверяется. `timeout_min` — **полётное** время, как у `reply`: пауза не идёт, ×N ускоряет. Исход — `MET` (условие выполнилось; в тот же тик побеждает таймаут) или `TIMEOUT`; он лежит в `reply.option` (`reply.timeout = true` при `TIMEOUT`), поэтому следующий `branch` разводит ветки `MET` / `TIMEOUT` (другие ключи — ошибка загрузки, как у `reply`). Состояние ожидания — `run.until = { step, deadlineMs }`, сериализуется; состояния старого формата читаются. Событие `WAIT_UNTIL {id, result}` — в журнал replay.
- **Случайные значения и циклы (T50).**
  - `draw: [{ weight?, set: { run.<имя>: значение | [min, max] } }, …]` — выбирает вариант по весу (целые 1..1000, по умолчанию 1) и даёт запуску значения `run.<имя>`; `[min, max]` — равномерное целое. Бросок — из seeded `Rng` сценария в момент шага, значения лежат в состоянии запуска (детерминизм и сериализация). Имя, которого нет у выбранного варианта, — `null`. `run.*` читают условия и шаблоны.
  - `loop: { until, stop?, every_min?, steps }` — повторяет `steps`; `until` (исход `MET`) и `stop` (исход `STOP`) проверяются на каждом тике, в том числе во время ожидания внутри цикла (оно сбрасывается), и при входе/возврате. Исход — в `reply.option`, следующий `branch` может иметь ветки `MET` / `STOP` и ответы тела цикла. `loop.min` — полётные минуты с входа в цикл. Внутри цикла должно быть ожидание (иначе ошибка загрузки), вложенных циклов нет. `break: true` выходит из цикла с последним ответом.
  - `wait: { reply: { options, timeout_round: true, default } }` (только в цикле с `every_min`) — тайм-аут не через N минут, а на ближайшей границе раундов `вход + k × every_min` полётного времени: ответ пилота внутри раунда не сдвигает сетку. `reply.timeout = true`, когда раунд закончился.
  - `if: "<условие>", steps: [шаги]` — шаги выполняются, только если условие истинно в момент шага; `break` внутри — выход из цикла.
  - Шаблон `{flight.now|plusmin:20|hhmm}` — время через 20 минут. Переменные `flight.holding` (удержание объявлено сценарием, `set: flight.hold`) и `flight.hold_fuel_low` (топливо дошло до `alternate_burn + reserve` + 10 %; без показания топлива — запас `extra + contingency` по среднему расходу крейсера OFP израсходован; `false` вне ожидания).
  - Сценарии: `drone_activity` (30 мин – 3 ч), `dest_fire` (20 мин – 2 ч), `runway_closure_dest` (30–60 мин по причине FOD/BIRD STRIKE, 60–180 мин DISABLED ACFT, в 3 из 30 случаев — закрыт до отмены: диверсия на первом обновлении). Обновление каждые 20 мин с новым временем (XATC присылает новый UM93 при каждом обновлении), отбой — когда выпавшее время вышло, не по сетке; цикл прекращается при `flight.divert != null` и посадке. `hold_fuel_watch` — «MIN DIVERSION FUEL» (ответ DIVERT / STAY, без ответа за 5 мин — DIVERT).
- **`resend: { of: [id, …] }`** — повтор последнего сообщения одного из сценариев этого рейса (дословно). Переменная `flight.sent` — id сценариев, уже что-то отправивших (`'final_loadsheet' in flight.sent`).
- **Команды пилота** — триггер `on: command`, `command: REQ_WX | REQ_GATE | REQ_LOADSHEET | DELAY | DIVERT | ETA | HELP | MEDICAL | REQ_ATIS | RDY | REQ_GATE_CHANGE` (cooldown по умолчанию `none`: отвечать на каждую). Синтаксис: `REQ WX [ICAO]` (`REQ METAR`; без аэропорта — назначение), `REQ GATE`, `REQ LOADSHEET` (`REQ LS`), `DELAY <1–600> [причина]`, `DIVERT <ICAO>`, `ETA`, `HELP`; **T44:** `MEDICAL [текст]` (только в воздухе), `REQ ATIS [ICAO]`, `RDY` (до OUT), `REQ GATE CHANGE [гейт] [причина]` (до IN); лишние слова игнорируются. Доп. переменные запуска T44: `cmd.atis`, `cmd.atis_code`, `cmd.gate`, `cmd.new_gate`, `cmd.divert_nm`, `cmd.divert_eta` (расстояние и ETA — только для аэропортов из OFP при GS ≥ 60 kt). Переменные запуска: `cmd.name`, `cmd.text`, `cmd.icao`, `cmd.minutes`, `cmd.reason`, `cmd.metar` (METAR из OFP для вылета/назначения/запасных, иначе null — до T13). Часть команды делает ядро (детерминированно, до сценариев): `DELAY` до OUT прибавляется к задержке рейса — как поздний старт (`est_*`, триггеры `sched_*`/`est_*`, `flight.delay_min`; уже отправленные сообщения не повторяются); `DIVERT` только в воздухе (OFF есть, ON нет) и не на назначение — `flight.divert`. Прилётные сценарии базового набора (`dest_weather`, `landing_data`, `gate_assignment`, `arrival_info`, `welcome_turnaround`) при диверсии не идут; перестроение маршрута на запасной — нет.
- **Каждая команда получает ответ.** Неизвестная — `UNABLE <текст> / SEND HELP FOR LIST`; известная с неверными аргументами или невыполнимая — `UNABLE <КОМАНДА> / <почему или формат>`; известная, но без включённого сценария — `RCVD <текст>`. Это сообщения самого ядра (`scenarioId: '#ops'`), через форматтер.
- Обработчики — `packages/scenarios/commands/*.yaml` (11 файлов: `cmd_help`, `cmd_req_wx`(+`_no_data`), `cmd_req_gate`(+`_divert`), `cmd_req_loadsheet`(+`_none`), `cmd_delay`, `cmd_divert` — с вопросом о причине и ветками, `cmd_eta`, `cmd_eta_ground`). Варианты одной команды разводятся условиями. Приложение и `pnpm replay` грузят их вместе с базовым набором; в настройках они отключаются как обычные сценарии.
- Новый форматтер шаблона `or:ТЕКСТ` — текст вместо `----` для пустого значения (`{cmd.reason|or:NOT GIVEN}`).
- Запись полёта: строка `tick` получила необязательное поле `inbound`; `pnpm replay run … --pilot "<мин>=<текст>"` добавляет сообщения пилота к прогону.
- Тесты: `core/test/two-way.test.ts` (парсер, reply/branch/таймаут/вложенность, сериализация посреди вопроса, потеря телеметрии, команды), `scenarios/test/commands.test.ts` (все команды на 3 синтетических полётах × 3 профиля, разговор целиком, эталон `reference/scenarios/medical_onboard.yaml` без `set`/`calc.*`).
- **Случайный старт в фазе и аэропорт в ответе (T51).** `trigger: { on: phase, phase: CRUISE, window: { after_min: 10, before_tod_min: 30 } }` — сценарий не стартует на фронте, а откладывается на случайный момент: после броска `probability` из seed берётся доля пути `f`, старт при `flight.minutes_to_tod ≤ T0 − after_min − f × (T0 − after_min − before_tod_min)` (T0 — значение на фронте): равномерно по пути, пауза и ×N не сдвигают. В момент старта заново условия, cooldown, excludes; «запустить сейчас» идёт без окна. Ответ `DIVERT <ICAO> …`: `reply.icao` — аэропорт, если ядро его знает (OFP, резерв T50, найденный приложением в `airports.csv` — ядро шлёт `DATA_REQUEST` `place` и ждёт `dataWaitMs`; не назначение, только в воздухе), остаток — `reply.arg`; `reply.unknown` — `ZZZZ`. Шаблоны: `{a|else:b.c}` — другая переменная вместо пустой, строка с `~` в начале пропускается, если в ней есть пустое значение. `flight.divert_nm` — расстояние до аэропорта диверсии, если известны его координаты.

## Интервал между сообщениями

- `CoreOptions.minGapMs` (по умолчанию 0): telex выходят из ядра не чаще одного за интервал по часам (`Clock`); остальные ждут в очереди ядра (`CoreState.outbox`, сериализуется) и уходят со временем выхода. Ответы пилоту (всё, что отправлено при разборе его сообщения: ответ на вопрос, команды, `UNABLE`/`RCVD`; поле `toPilot`) встают в очередь перед остальными. Причина: самолёты опрашивают Hoppie примерно раз в минуту, и близкие сообщения приходили пачкой (проверка человеком 2026-10-08). В приложении — настройка «Интервал между сообщениями» (по умолчанию 60 с, 0 — сразу), пишется в заголовок записи (`header.minGapMs`), replay её применяет; в статусе сети — «ждут интервала: N».

## Внешние данные (T13)

- **Ядро не ходит в сеть** (инвариант 3). Данные — вход ядра `CoreInput.data: ExtDataUpdate` (`core/src/ext/data.ts`): `wx` (METAR/TAF по аэропортам, `null` = отчёта нет), `atc` (станции VATSIM аэропортов вылета и назначения), `events` (EONET), `stands` (стоянки OSM назначения). Каждое поле заменяет прежнее; данные хранятся в состоянии движка (`ext`, сериализуется) и пишутся в запись полёта (`tick.data`), поэтому replay детерминирован.
- **Переменные**: `wx.{orig,dest,altn}_metar` — живой METAR, иначе из OFP; `_live` — живой ли; `_obs` — время наблюдения; `_taf` — только живой. Живой = не старше 3 ч. `ext.{orig,dest}_atc` — строки `ПОЗЫВНОЙ ЧАСТОТА` (ATIS, DEL, GND, TWR, APP), `_atc_count` (null без данных или если данным VATSIM больше 20 мин), `ext.dest_atis` — буква ATIS. `ext.event_*` — ближайшее событие EONET **впереди по маршруту** в пределах 150 NM от него: `id`, `title`, `category` (`SEVERE STORM`, `WILDFIRE`, `VOLCANO`…), `ahead_nm` (по маршруту от самолёта), `off_nm` (от маршрута). Положение события относительно маршрута считается один раз при получении (ломаная OFP с шагом ≤ 10 NM).
- **Гейт из OSM**: при стоянках назначения `ops.arr_gate` берётся из них (гейты, если их ≥ 3, иначе стоянки; натуральный порядок; одна выборка Rng `<seed>/#stands`). Как только сообщение с `ops.arr_gate` ушло, новые стоянки игнорируются (`ext.gateLocked`) — гейт в `gate_assignment`, `REQ GATE`, `arrival_info` один и тот же.
- **`REQ WX` с запросом данных**: при `dataWaitMs > 0` (приложение с живыми данными — 60 с) и без свежей (≤ 15 мин) погоды аэропорта ядро откладывает команду и выдаёт событие `DATA_REQUEST {kind: wx, icao}`; ответ — когда данные пришли или вышло время (тогда с тем, что есть: METAR из OFP или «нет данных»). Переменные: `cmd.metar` (живой или из OFP), `cmd.taf`, `cmd.wx_live`, `cmd.wx_obs`. Без источника данных (`dataWaitMs = 0`, по умолчанию) — ответ сразу.
- **Сценарии**: `packages/scenarios/external/` — `dest_weather_live` (вместо `dest_weather`, если у назначения живой METAR; `dest_weather` получил условие `!wx.dest_live`), `vatsim_atc` / `vatsim_atc_none` (за 80 NM до TOD, как в оригинале; без данных VATSIM — ничего), `natural_event` (в крейсере, событие ≤ 250 NM впереди, не позже 15 мин до TOD), `space_launch` / `space_launch_done` (T28: пуск ракеты, см. ниже). `commands/cmd_req_wx_live` (METAR + TAF), `cmd_req_wx` — только без живой погоды. `takeoff_data` берёт `wx.orig_metar`. Приложение и `pnpm replay` грузят `external/` вместе с `base/` и `commands/`.
- **Адаптеры** — пакет `@acars/data-sources` (см. `06`). Тесты: `core/test/ext-data.test.ts`, `scenarios/test/external.test.ts` (каждый сценарий на 3 полётах × 3 профиля с данными и без; весь набор с данными), `data-sources/test/adapters.test.ts`, `desktop/test/controller.test.ts` («live data»).

## Нестандартные сценарии и память авиакомпании (T14)

- **`set: { цель: значение, … }`** (`core/src/scenario/engine.ts`). Цели: `flags.<имя>` (`a–z0–9_`, до 40 символов) — **память авиакомпании**: видна всем сценариям этого рейса как `flags.<имя>` (нет — `null`) и переходит на следующие рейсы; `null` удаляет. `flight.divert` — диверсия рейса (ICAO; только в воздухе — OFF есть, ON нет — и не на назначение; иначе не применяется), как команда `DIVERT`. `flight.hold` (T48) — минуты ожидания в воздухе (1–120; `null` — конец), станция XATC даёт `HOLD AT` и EFC; `flight.delay_min` (T43) — поднять задержку рейса до N минут (только до OUT, как `DELAY`; меньшая не уменьшает) — так `slot_ctot` сдвигает `est_*` до CTOT; `ops.arr_gate` — гейт прибытия с этого момента (`A–Z0–9`, 1–6 символов; дальше `arrival_info`, `REQ GATE` называют новый). Значение — литерал (строка/число/bool/null) или шаблон; шаблон из одной переменной `{ofp.pax}` сохраняет тип (число остаётся числом). Строки обрезаются до 80 символов, флагов не больше 64. Любые другие цели (`flight.pax_delta` из черновика `reference/`) — ошибка загрузки. Каждое присваивание — событие `SET {id, name, value, applied}`.
- **Перенос между рейсами**: `CoreOptions.flags` на входе, `AcarsCore.flags` на выходе; состояние ядра сериализует их. Приложение хранит их в `<userData>/airline-memory.json`, сохраняет при «Завершить»/«Стоп», при старте пишет в ленту (`memory`) и в заголовок записи (`header.flags`, replay стартует с ними). В настройках — список и кнопка «Очистить» (не во время полёта). Привязка к самолёту/дате — дело сценария (`flags.mel_reg == ofp.ac_reg`, `flags.mel_date != flight.date`).
- **Данные нестандартных сценариев** — `irr.*` (`scenario/irregular-data.ts`, Rng `<seed>/#irr`, от опубликованного расписания, так что задержка приближает curfew и стыковку): `irr.curfew` (+ `_local` по `utc_offset` назначения, `_margin_min` — до оценки посадки с учётом задержки), `irr.connect_flight/_std/_pax/_margin_min/_left_min` (последнее — от текущего момента; `_pax` — 20–50 % от `ops.transfer_pax`, T41), `irr.tanker_kg/_block_kg/_ldw_kg`, `irr.flow_delay_min`, `irr.revised_ctot` (= `ops.ctot` + flow), `irr.latest_out` (оценка OUT + запас FDP), `irr.new_gate` (другая стоянка OSM или соседний номер, Rng `<seed>/#irr-gate`), `irr.lost_bags`, `irr.crew_change_min` (задержка смены экипажа, 40–90 мин шаг 5), `irr.crew_ready` (= `irr.latest_out` + она). Ещё: `flight.nearest_altn(_nm)` — ближайший к самолёту из вылета и запасных; `wx.orig_temp_c`, `wx.dest_temp_c` — из METAR (живого или OFP). **T33:** `wx.dest_wind_from` (откуда дует, ° истинные), `wx.dest_wind_kt` и `wx.dest_smoke_drift` (румб из 8, куда ветер несёт дым) — из METAR назначения; null при штиле, `VRB` и без METAR. Сценарий `dest_fire` (HOLD/DIVERT, продолжение через 20 мин) взаимоисключается с `drone_activity` и `runway_closure_dest`. **T31:** с настройкой «Имитация линии передачи» выход ядра задерживается линией (`OutboundMessage.link`, `datalink/link.ts`); сценарии об этом не знают. **T34:** шаг `smoke: start|stop` — дым у плановой ВПП назначения в симуляторе (команда `smoke` приложению: аэропорт и ВПП; координаты — OurAirports, объект создаёт мост при подлёте ≤ 40 NM, см. `bridge/msfs/README.md`); без моста и пакета ничего не происходит. **Пожар в случайной точке (2026-10-16):** `smoke: { start: orig | dest, along_nm, side_nm: [min, max] }` — у плановой ВПП вылета или назначения: до `along_nm` в обе стороны вдоль оси от середины и `side_nm` вбок от оси, сторона случайная (сотые NM, из seeded `Rng` сценария); команда `smoke` несёт `offset { alongNm, sideNm }` (вдоль — по направлению названной ВПП, вбок — плюс вправо), приложение берёт истинное направление ВПП из координат её торцов (OurAirports, `RunwayPoint.headingDeg`). Место — в `run.fire_at` для текста: `SE SIDE OF RWY 24L` (сторона — по номеру ВПП, магнитный курс; для названия румба из 8 этого хватает). Так работают `dest_fire` и `dep_fire` (пожар перед взлётом). `run.forced` — `true`, если сценарий запущен вручную («Запустить сейчас»): `dep_fire` тогда не ждёт случайный момент.
- **Набор** — `packages/scenarios/irregular/` (23, все из списка `02`): `medical_onboard` (CONTINUE/DIVERT → `flight.divert` ближайший), `unruly_passenger` (RESTRAIN/DIVERT/CONTINUE) → `unruly_followup` на следующем рейсе, `tech_defect_mel` (CONFIRM/NEGATIVE) → `mel_carry_over` на следующем рейсе того же борта (закрытие после прилёта), `deicing_holdover` (OAT ≤ 3 °C, READY), `curfew_dest` (запас < 20 мин; UNABLE → диверсия на запасной), `tankering` (ACCEPT/DECLINE, если LDW позволяет), `short_connection` → `connection_made` (≥ 40 мин до STD) / `connection_held` (15–40, рейс ждёт) / `connection_missed` (< 15) по фактическому ON_BLOCK, `dg_notoc` (ACK), `vip_onboard`, `runway_closure_dest` и `drone_activity` (HOLD/DIVERT, взаимоисключаются), `altn_wx_deterioration` (OK/LOW), `crew_duty_limit` (задержка ≥ 30 мин; EXTEND/NO) → `discretion_followup`, `atc_flow_delay`, `lost_baggage` → `rush_bags_followup`, `gate_reassignment` (после `gate_assignment`, `set ops.arr_gate`). Вероятности малы (0,03–0,08; реакции на условия — выше): 0,3–2 события на рейс. **T41:** HOLD у `drone_activity` / `runway_closure_dest` продолжается до отбоя «ARRIVALS RESUMED» (с T50 — случайный срок и обновления, см. «Случайные значения и циклы»); `altn_wx_deterioration` (OK) присылает обновление перед TOD (живой METAR запасного, иначе общий текст); `medical_onboard` — «DOCTOR ON BOARD NO» усиливает рекомендацию, текст пилота после ответа (`reply.arg`) попадает в ответ, на ON_BLOCK — медики у двери; `unruly_passenger` (RESTRAIN) — полиция у двери на ON_BLOCK; `crew_duty_limit` (NO) — смена экипажа, если к `irr.latest_out` нет OUT; `gate_reassignment` — строка о ленте багажа; `vip_onboard` — место `{seat:1-2}`. **Идиома «если»:** `wait: { until: <условие>, timeout_min: 0.02 }` + `branch: MET / TIMEOUT` — условие проверяется сразу, ложное = `TIMEOUT` через секунду полётного времени. **Срок жизни флагов памяти** (`core/src/scenario/flags-expiry.ts`, по `*_date` = плановый OUT рейса, при старте рейса): MEL 10 дней, no-fly (`unruly_*`) и `crew_discretion_*` 30, `rush_*` 3; семейство без даты не трогается. **T42:** `dg_notoc` — UN3481 с `IMP RLI/ELI`, сухой лёд в кг, позиция `{hold}`; `tech_defect_mel` — пункты MMEL по семейству (A320, B737; прочие типы — общие пункты без источника). Временные флаги внутри одной цепочки (`deice_pad`, `vip_seat`) сценарий очищает сам.
- **Тексты для интерфейса**: необязательные поля `title_ru`, `description`, `description_ru` — только для приложения (вкладка «Сценарии», список «Запустить сейчас»), по языку интерфейса; без перевода показывается английский `title`. Телексы всегда на английском (`08`, решение 7). Заполнены у всех `irregular/`.
- **Подсказки к сообщениям** (T57, только для приложения, в сеть и в FMS не уходят): `hint` / `hint_ru` сценария — 1–3 предложения обычным языком: кто прислал, о чём сообщение, чего ждут от пилота; в отличие от `description` не раскрывает исходы и не содержит чисел, которых нет в сообщении. У шага `send` — свои `hint` / `hint_ru`, если сообщения сценария различаются по смыслу (ветки ответа, обновления, сообщение по прилёте); иначе берётся подсказка сценария. У `wait: { reply }` — `reply_hints` / `reply_hints_ru`: `{ ВАРИАНТ: «что значит этот ответ» }`, ключи — ровно `options` (проверка при загрузке). Русская подсказка без английской — ошибка загрузки. Для команд пилота первое предложение `hint` — что делает команда (окно «Запрос»). Заполнены у всех встроенных сценариев (тест `packages/scenarios/test/index.test.ts`). Ядро отдаёт приложению только состояние ожидания (`AcarsCore.pendingReplies`: сценарий, шаг `wait_reply`, варианты, `default`, остаток полётного времени) и номер шага `send` в `OutboundMessage.step`; запись полёта и replay не меняются.
- **Вероятность вручную** (настройки → Сценарии): у каждого нестандартного события (`irregular`, кроме обработчиков команд, т. е. без `cmd_divert`) поле «%» (0–100, шаг 0,1; пусто — значение `probability` из файла). Хранится в `settings.chances`, применяется со следующего рейса: приложение передаёт ядру сценарий с заменённой `probability`; отличия от файлов пишутся в заголовок записи (`header.probabilities`, 0–1), replay применяет их.
- **«Запустить сейчас»** (экран полёта, пока идёт рейс): вход ядра `CoreInput.force: [id]`. Сценарий стартует на этом тике без триггера, вероятности, кулдауна и `excludes`, но **только если выполнены его условия** (фаза, задержка, флаги — иначе сообщения были бы бессмысленны) и он не идёт сейчас. Итог — событие `FORCED {id, result: started | conditions | running | unknown, detail}` (для `conditions` — текст невыполненного условия), в ленте приложения — `forced_*`. Пока телеметрия потеряна, запрос ждёт в состоянии ядра (`forced`). Запись полёта: поле `force` строки `tick`, replay его воспроизводит.
- Тесты: `core/test/flags.test.ts`, `scenarios/test/irregular.test.ts` (каждый сценарий на 3 полётах × 3 профиля **по каждому варианту ответа**, цепочки внутри рейса и между рейсами, детерминизм), `desktop/test/controller.test.ts` («airline memory»), `replay.test.ts`.

## Табло VDGS (T22)

- **`vdgs: { narrow: [строки], wide?, x?, small?, duration_sec? }`** — текст на табло VDGS от GSX в аэропорту прилёта (или диверсии). Строка — шаблон или `{ red: шаблон }`. Лимиты: small 4×2, narrow 6×6, wide 9×7, x 10×7 (`core/src/sim/vdgs.ts`, источник — `06`, «GSX VDGS»). `narrow` обязателен, `wide`/`x` без своих строк берут `narrow`, `small` — только если задан. Символы A–Z, 0–9, пробел, `- / . :`; нижний регистр переводится в верхний. Литерал, который не помещается, — ошибка загрузки; шаблон — `SCENARIO_ERROR` при выполнении, без сокращений. `duration_sec` 1–60, по умолчанию 6.

- Набор — `packages/scenarios/sim/`: `vdgs_arrival` (после посадки: авиакомпания, рейс, аэропорт вылета, гейт).
- Тесты: `core/test/vdgs.test.ts`, `scenarios/test/sim.test.ts`, `apps/desktop/test/vdgs.test.ts`.

Считаются один раз на рейс из OFP и Rng `<seed>/#ops`, не сериализуются (выводятся заново). Это детерминированная логика ядра (инвариант 8), а не `set`; `set` по-прежнему T12/T14. **Следующий рейс (T53):** `ops.next_flight`, `ops.next_orig`–`ops.next_dest`, `ops.next_std`. После рейса в хаб авиакомпании (настройка «Мой хаб», иначе OpenFlights) — маршрут компании из хаба для этого типа ВС (Rng `<seed>/#next`) и случайный номер той же длины; иначе и без подходящих маршрутов — обратно, номер + 1. Опция ядра `nextLegVersion` (1 — всегда обратно, как в записях до T53) и `hub` пишутся в заголовок записи. **T55 (`nextLegVersion: 3`, в приложении по умолчанию):** сначала реальный вылет авиакомпании из аэропорта назначения (`CoreInput.data.connex`): операторский (не код-шеринг), не раньше STA + `ops.turnaround_min`, не в аэропорт вылета, того же семейства T40 по тексту `aircraft.model` (`ext/aircraft-models.ts`); номер — ICAO-код компании + цифры реального номера, место и STD реальные (Rng `<seed>/#next-live`). Иначе маршрут компании из статистики маршрутов (`CoreInput.data.routes`, `ext/routes.ts`), вес — `averageDailyFlights`, номер случайный, STD = STA + оборот. Иначе как в версии 2. `ops.next_src` — `SRC AERODATABOX` (последняя строка `next_leg`, `aircraft_change`, `welcome_turnaround`), когда рейс взят из данных AeroDataBox, иначе пустая строка.
- LMC по оригиналу: ±5 пакс с p = 0.5, ±200 кг груза (шаг 10) с p = 0.5; масса пассажира = `pax_weight + bag_weight` из OFP (иначе 84 кг). Underload = min(MTOW, MZFW + TOF, MLW + TIF) − TOW.
- Лента и транзитные пассажиры — заглушки; гейт — из стоянок OSM, если они есть (T13, ниже), иначе заглушка. Погода — живая (T13) или METAR из OFP (на момент выпуска OFP, о чём сказано в сообщении). В `takeoff_data` нет V-скоростей: их нет в OFP.
- `{name:*}`: «страна авиакомпании» в OFP отсутствует, вместо неё регион ICAO аэропорта вылета (`core/src/scenario/names.ts`).
- Тест `packages/scenarios/test/base.test.ts`: каждый сценарий отдельно (probability = 1) на 3 синтетических полётах (норма; уход на второй круг + пауза + ×4; OFP в lbs без номера рейса + разрыв телеметрии) × 3 профиля дисплея; весь набор на одном полёте — порядок, снапшот, согласованность LMC и гейта.

## Группы сценариев (T39)

- Поле сценария `group: <имя>` (snake_case). Описание групп — `packages/scenarios/src/groups.ts` (`SCENARIO_GROUPS`: имя → `max_per_flight`); имя, которого там нет, — ошибка загрузки (`withGroups` в ядре, зовётся загрузчиком пакета). `compileScenario` сам лимита не знает: без загрузчика `groupMax = null`, ограничения нет.

Принудительный запуск («Запустить сейчас») лимит обходит, как и `excludes`. Счётчик — `starts` сценариев в состоянии, отдельного поля нет.

## Тип самолёта (T40)

- Переменные из `ofp.aircraft.icao` (`core/src/scenario/aircraft.ts`; неизвестный тип — `null`): `aircraft.family` (A320, A330, A350, A380, B737, B747, B777, B787, E-JET, CRJ, ATR, DH8), `aircraft.maker`, `aircraft.body` (`NARROW`/`WIDE`), `aircraft.alert_sys` (`ECAM`/`EICAS`; у ATR и DH8 `null`).
- **Таблица кодов типов не сверена с ICAO Doc 8643** (выгрузки данных не было; решение пользователя 2026-10-14) — `[ПРОВЕРИТЬ]` на реальных OFP. Названия отсеков и виды ULD — из Airbus AC (A320 Rev. 44, A330 Rev. 32) и Boeing ACAPS 737NG (Rev C); кодов позиций ULD в них нет, поэтому номера позиций не генерируются. Буквы мест — допущение (компоновка зависит от авиакомпании).

### T43/T44: гейт, слот, топливо (2026-10-14)

- **Гейт не выдумывается.** `ops.arr_gate` = `null`, пока нет реальных стоянок OSM. Для текстов — `ops.gate_known`, `ops.gate_place` (`GATE A12` / `STAND 12` / `GATE TBA`), `ops.gate_line` (`… CONFIRMED` / `GATE WILL BE ADVISED`), `ops.gate_expected`, `ops.ground_support` (`GPU AND PCA AVBL` для гейта, `REMOTE STAND, BUS AND STAIRS` для стоянки без `aeroway=gate`, `GROUND SUPPORT TBA`). Без стоянок `gate_assignment`, `gate_reassignment` и VDGS не идут. `irr.new_gate` = `null`, если другой стоянки нет.
- **Слот.** `slot_ctot` ставит `set: flight.delay_min` (задержка не ниже N минут, только до OUT); CTOT, объявленный слотом, не сдвигается задержкой, которую вызвал сам слот (`delayRaisedMs`). `slot_missed` — взлёт позже CTOT + 10 мин (окно −5/+10, AIP Ирландии ENR 1.9 от 18.05.2023); нового CTOT не выдумывает. `RDY` — окно EOBT−15 мин … CTOT−руление, шанс улучшения 40 %, выигрыш 5–15 мин (допущения).
- **T46.** `flight.touchdown_fpm` — скорость снижения на касании, фут/мин: движок читает `touchdownFpm` телеметрии один раз, когда записан ON (SimVar `PLANE TOUCHDOWN NORMAL VELOCITY` держит значение прошлой посадки, поэтому раньше ему верить нельзя); `null` без поля или с нулём. `flight.fuel_below_plan_kg` — запланированное топливо на борту в этой точке маршрута (`OfpFix.planFobKg`, интерполяция по пройденной дистанции, без экстраполяции) минус фактическое, кг (плюс — ниже плана), только в воздухе; `flight.fuel_plan_tol_kg` — допуск в этой точке (5 % плана, не меньше 500 кг). Нет плана в OFP или телеметрии — `null`. Сценарии: `hard_landing_check` (ON_BLOCK, > 350 фут/мин, CONFIRM → флаги `hardland_reg/date`, срок 3 дня), `hard_landing_followup`, `fuel_monitoring` (CRUISE, `wait: until` до 12 ч, ответы WX/ATC/LEAK/NORMAL), `ped_fire_cabin` (0,5 % за рейс — меняется в приложении, как у остальных нестандартных).
- **Топливо.** `fuel_slip`: триггер STD−18, ждёт `flight.fuel_stable` (после заправки топливо не менялось больше 100 кг минуту) до STD−12; `flight.fuel_uplift_kg`, `flight.fuel_diff_kg`.
- **Стыковка.** `irr.connect_flight` = `ONWARD FLT`, если авиакомпания рейса выполняла собственные вылеты из аэропорта назначения по OpenFlights (`ext/airline.ts`, данные 2014 г.; номера рейса нет), иначе `null` — `short_connection` (а с ним `connection_*`) не идёт. STD стыковки после STA — по `ofp.airline_type` (`ext/airline.ts`): лоукостер 50–70 мин, хаб-перевозчик 100–140, прочие 50–95; оборот `ops.turnaround_min` — 45–55 / 105–135 / 50–70 (тяжёлые 75–95). Тестовый хук `syntheticConnections` включает синтетический рейс с номером. **T30:** с ключом AeroDataBox пользователя реальный вылет авиакомпании (`CoreInput.data.connex`, ниже) заменяет и `ONWARD FLT`, и синтетический рейс: `irr.connect_flight` — номер (`JX862`), `irr.connect_std` и `_margin_min`/`_left_min` — от его STD; `irr.connect_dest` — куда летит, `irr.connect_gate` — гейт, иначе `TERM <терминал>`, иначе null; `irr.connect_src` — `SRC AERODATABOX` (последняя строка `short_connection`/`connection_*`, атрибуция по условиям), без реального рейса — пустая строка (форматтер убирает пустую последнюю строку). `irr.connect_pax` остаётся синтетическим (C7). **T55** (`nextLegVersion: 3`): «есть вылеты из аэропорта назначения» — да, если в `connex` есть операторский вылет компании или в `routes` есть маршрут с ней; иначе OpenFlights, как раньше.
- **TLR и экипаж OFP.** `ofp.to_flaps`, `ofp.to_thrust` (`FLEX 71` / `TOGA`), `ofp.v1|vr|v2`, `ofp.ldg_flaps`, `ofp.vref` — из TLR SimBrief, только если TLR посчитан для ВПП по плану OFP (иначе `null`); `ofp.crew_cockpit`, `ofp.crew_cabin` — численность из `crew` OFP. `takeoff_data` / `landing_data` добавляют строки `FLAPS … V1 … VR … V2 …` / `FLAPS … VREF …`, `final_loadsheet` — `CREW 2/16` и `OEW`; `ops.cabin_crew` — из OFP, если есть. Без TLR / экипажа — прежний текст в момент триггера (ветка «если» MET), с ними — на тик позже (TIMEOUT). Записи до T43 без этих полей читаются как `null`.
- **Имена (`{name:crew}`, `{name:ops}`), версия 2.** `names.region` — по стране авиакомпании (OpenFlights), иначе страны аэропорта вылета (VATSpy), иначе `null` (префикс ICAO, как в версии 1); `names.mix` — `some` (каждое десятое имя из другого региона) или `all` (UAE, ETD, QTR: любой регион). Опция ядра `namesVersion` (1/2, по умолчанию 2) пишется в заголовок записи; replay без поля — версия 1.
- **Коды задержки.** `flight.delay_codes` — элемент `DL` MVT (`DL81/63/0025/0010`) после OUT позже STD, иначе `null`; части задержки — `delayParts` в состоянии движка (поздний старт `63`, слот `81`, `DELAY` пилота — код из причины), `core/src/scenario/delay-codes.ts`. `departure_report` / `block_report` добавляют строку последней.
- **Диверсия.** `divert_arrival` на ON_BLOCK и флаги `recovery_*` (3 дня, `flags-expiry.ts`) → `recovery_followup` на следующем рейсе из этого аэропорта.
