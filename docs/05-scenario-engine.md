# 05 — Scenario engine

Scenarios are described in YAML, validated with JSON Schema, and executed deterministically by the core (seeded Rng). Examples are in `reference/scenarios/`.

## Model

```yaml
id: string                 # unique, snake_case
version: 1
category: docs | ops | irregular | external | fun
title: string              # for the settings UI
enabled_by_default: bool
trigger:                   # when the scenario becomes a candidate
  on: phase_enter | phase | event | time | distance
  phase: CRUISE            # for phase_enter / phase
  event: OOOI_OFF          # for event
  at: { rel: sched_out, offset_min: -25 }       # for time
  dist: { to: tod, lte_nm: 150 }                # for distance
conditions:                # all must hold
  - "ofp.block_time_min >= 90"
  - "aircraft.cat in ['M','H']"
probability: 0.05          # 0..1, rolled once when it becomes a candidate
cooldown: per_flight | per_session | { minutes: 120 }
excludes: [other_scenario_id]   # mutual exclusion
group: special_news        # group (T39): the max_per_flight limit is in packages/scenarios/src/groups.ts
operations: [sched_pax, charter_pax]   # flight kinds (T89); no field means all kinds
# charter: [tour]          # charter types (T107, only with operations: [charter_pax]); no field means all types
# charter_probability: 1   # probability when the user picked the charter type themselves (T107); no field means probability
priority: 0                # on conflict within one tick
steps:                     # sequence
  - send: template_id | inline text
    vars: { ... }          # local variables
  - wait: { minutes: 5 } | { phase: DESCENT } | { reply: { options: [CONTINUE, DIVERT], timeout_min: 10, default: CONTINUE } } | { until: "flight.dist_to_tod_nm < 80", timeout_min: 90 }
  - branch:
      DIVERT: [ { send: ... } ]
      CONTINUE: [ { send: ... } ]
  - set: { flags.mel_item: "21-31-01" }   # affects later scenarios and the next flight
```

## Templates

- Syntax: `{var}`, `{var|fmt}`. Formatters: `kg1` (12345 → 12.3), `hhmm`, `ddmmm`, `pad:N`, `upper`, `qnh`.
- Generators: `{rand:10-35}`, `{pick:[A,B,C]}`, `{name:crew}` (by the airline's country), `{seat}` (letters by aircraft type, T40; `{seat:1-2}` — rows 1–2 only, T41), `{hold}` (hold compartment: `FWD/AFT/BULK HOLD`, plus `LD3`/`PALLET` on widebodies).
- Template blocks: `header` / `body` / `footer`. Lines and separators are inserted by the formatter according to the `DisplayProfile`.
- All variables come from the context: `ofp.*`, `tm.*` (telemetry), `phase`, `flight.*` (OOOI, seed, flags), `wx.*`, `ext.*`.

## Execution

1. On every tick the core computes the set of candidates from `trigger` and `conditions`.
2. For new candidates: a (seeded) `probability` roll. Check `cooldown`, `excludes` and the group limit.
3. Active scenarios run as coroutines over `steps`. `wait` puts the scenario into waiting for an event.
4. Outgoing messages → formatter → transport queue (rate limit).
5. An incoming pilot telex is matched against pending `reply` waits. If there are none, against the global "commands" (`REQ WX`, `REQ GATE`…).

## Incoming pilot commands (v1)

| Command | Reply |
|---|---|
| `REQ WX <ICAO>` | METAR/TAF |
| `REQ GATE` | assigned gate and stand |
| `REQ LOADSHEET` | repeat of the last loadsheet |
| `DELAY <min> <reason>` | acknowledgement, schedule shift |
| `DIVERT <ICAO>` | diversion chain |
| `ETA` | ETA and connection data |

The parser is tolerant of whitespace and case. An unknown command → a polite `UNABLE / SEND HELP FOR LIST`.

## Content validation

- JSON Schema plus a test that runs every scenario on 3 synthetic flights and checks that templates expand, lines are ≤ the profile width, and there are no forbidden characters.
- LLM (optional): a `send` step may have `llm_flavor: true`. The backend then rephrases **only** free text. The result passes the same checks; on failure the original template is used.

## Implementation v0 (T06)

- Code: `packages/core/src/scenario/` (types, conditions, templates, context, engine), `packages/core/src/core.ts` (`AcarsCore`: FSM + engine per the contract in `03`), `packages/scenarios/src/` (YAML 1.2 → JSON Schema → `compileScenario`).
- Triggers: `phase_enter`, `phase`, `event` (FSM events except `TELEMETRY_LOST`), `time` (`rel`: `sched_*`, `est_*`, actual `out/off/on/in`), `distance` (`to: dest | tod | orig`, `lte_nm` / `gte_nm`). Steps: `send`, `wait: { minutes }`, `wait: { phase }`; `reply`, `branch` — T12 (see below), `set` — T14 (see below).
- A candidate = the trigger **and** the conditions became true on this tick (an edge). Then cooldown, group limit, `excludes` (both ways), the `probability` roll; start by `priority` (descending), then by `id`.
- Each scenario has its own Rng with seed `<seed>/<id>`: adding a scenario does not change the rolls of the others.
- `wait.minutes` counts FSM "flight time" (× `simRate`, without pauses); `time` triggers follow the `Clock`. While telemetry is lost, the engine stands still.
- Variables — `CONTEXT_VARIABLES` in `scenario/context.ts` (`ofp.*`, `aircraft.*`, `tm.*`, `flight.*`, `phase`); an unknown variable is a load error. A missing value is printed as `----`.
- Formatters: `kg1`, `hhmm`, `ddmmm`, `pad:N`, `lpad:N`, `int`, `upper`, `qnh` (T13: the `Q1013`/`A2992` group from the METAR). Generators: `rand`, `pick`, `seat`; `name:*` — T07.
- T07 added: the `sign` formatter (+3 / -120 / 0), the `{name:crew}` / `{name:ops}` generators.
- **Mass units (T105).** Masses in the context are always in kg (`*_kg`); the message unit is the core option `massUnit`: `ofp` (as the OFP was planned, `Ofp.source.plannedUnit`), `kg`, `lb`; without the option — `kg` (recordings before T105). Variables `units.mass` (`KG` / `LB`) and `units.mass_big` (`TONNES` / `1000 LBS`). Formatters: `w1` — a large number (tonnes or thousands of pounds, one decimal: `180.2` / `397.3`), `w` — whole KG / LB (for LMC and fuel difference: `{load.cargo_lmc_kg|w|sign} {units.mass}`), `wt` — with the unit (`12.3 T` / `27100 LB`, pounds up to a hundred — the same precision as `w1`). `kg1` remains (always tonnes) for community packs. 1 lb = 0.45359237 kg (exact). Dangerous-goods quantities in the NOTOC (`dg_notoc`, `NET 25 KG`) are not converted: IATA DGR uses kg.
- **Late start** (user decision 2026-10-08, after the T10 check: when started 5 min before STD, five pre-departure telexes arrived at once and out of order). On the first tick the engine computes a delay: if less than `lateStartLeadMin` remains until `sched_out` (35 min by default — the length of boarding in the synthetic profile), the flight is considered delayed by the missing time, rounded up to 5 min. `time` triggers with `rel: sched_*` and `est_*`, the variables `ofp.est_*`, `ops.ctot`, `ops.next_std` are shifted by the delay; `ofp.sched_*` (STD/STA in the texts) are not. The variable `flight.delay_min` is the delay in minutes (0 — on time). The delay is part of the engine state (`delayMs`); the same (OFP, recording, seed) gives the same delay. Scenarios whose time has already passed by the start of a delayed flight (for example `crew_info` at 45 min) go out on the first tick. **Fitting into the remaining time** (user decision 2026-10-18, `lateStartVersion: 2`; the app enables it and writes it to the recording header; without it — version 1, as above): the delay is declared only when less than 20 min remain. If less remains until STD than the earliest `sched_out − N` trigger (currently 60 min), the `sched_out − N` offsets are multiplied by `(remainder − 1 min) / largest N` — for example, 30 or 50 min before STD all the documents arrive, in the same order and proportions, and all before STD. The coefficient is kept in the state (`preScale`). **Only scenarios that can fire** (user decision 2026-10-22, `lateStartVersion: 3`, the app writes it to the recording header): when started 27 min before STD, the first telex arrived after 7.5 min, because the "largest N" came from `discretion_followup` (−60), which needs a flag from a previous flight. In version 3 the largest N is taken on the first tick only among scenarios that can still start: not excluded by a condition on values known at the start (`flags.*`, `ofp.*`, `phase`), by a cooldown, or by the first probability roll (the roll is peeked on a copy of the scenario's Rng; the real roll is the same). Conditions on live data (`tm.*`, `wx.*`, `ext.*` …) do not exclude — they can still become true. **All documents before pushback** (T61, user decision 2026-10-27, `lateStartVersion: 4`, the app writes it to the recording header; versions 1–3 replay as before): the late-start delay (less than 20 min to STD, code 63) is still declared, but it shifts only the estimated times (`ofp.est_*`, CTOT, `departure_report`), not the `sched_out − N` triggers. If less than the largest N remains until STD (as in version 3), those triggers are fitted into the window `[start, STD − 2 min]`: time = `STD − 2 min + N · coefficient`, coefficient = `(STD − 2 min − start) / largest N` (not less than 0; from 2 min before STD — all at once, the outbox releases them one at a time per `minGapMs`). The window and shift are in the state (`preScale`, `preEndMs`, `preShiftMs`). `set: flight.delay_min` (the `slot_ctot` slot and others) does not shift documents; the pilot command `DELAY` does (`preShiftMs`). Pre-departure scenarios start after the others, in trigger order (earlier N — earlier; on a tie — priority); a document (`category: docs`) does not start while an earlier document is running (for example `fuel_slip` waits for fuel to stabilise — `final_loadsheet` waits for it). **Flush** on the OOOI OUT tick or on entering PUSHBACK (whichever is first, once): the `wait: until` and `wait: minutes` waits of pre-departure scenarios end immediately (`until` — with the outcome `MET`/`TIMEOUT` by the current data), pre-departure scenarios that have not started and whose time has not yet come start (probability and cooldown as usual), and their conditions on `phase` read the phase before pushback; the `PREDEP_FLUSH` event with a list of ids goes to the app feed and the replay report. Waiting for a pilot reply (`wait: reply`) is not interrupted. "Before pushback" is a game rule: EU 965/2012 CAT.POL.MAB.105(a) requires load documentation "prior to each flight" and does not name the moment (before OUT) (checked 2026-11-07, UK CAA Regulatory Library).
- **OFP date** (user decision 2026-10-22: a SimBrief plan for tomorrow — STD 23.10 12:15Z with a start at 22.10 11:43Z — produced a flight without pre-departure messages). When a flight starts, the app (`alignOfpDay`, `packages/core/src/ofp/align.ts`) shifts all absolute OFP times (`sched_*`, `est_*`) by a whole number of days so that STD is the nearest to the flight clock (with "sim time" — to the simulator time), no farther than ±12 h; the time of day stays as in the plan. Example: a plan for 00:30Z with a start at 23:50Z — STD tomorrow at 00:30Z; a plan for 09:00Z with a start at 11:00Z — STD today, and the flight is considered started late. The feed gets a system line `ofp_date` (plan date and flight date). The core receives, and the recording stores, the already shifted OFP; replaying a recording matches the live run.

## Two-way communication (T12)

- **Core input** — `CoreInput.inbound: PilotMessage[]` (`{ from, type, text }`, the contract in `03`). The app passes with the nearest tick: telexes received by the transport and the text typed in the "Reply as pilot" window (for aircraft without free telex — A350/A380, `06`; it does not go to the network). Only `type: telex` from the flight's callsign is accepted; CPDLC (A350/A380 logon), foreign callsigns and empty messages produce a `PILOT_MESSAGE` event with `result: ignored`. While telemetry is lost, messages wait in the core state (`inbox`).
- **Normalisation**: upper case, everything except `A–Z0–9` → space (`REQ-REFUEL` from Fenix, `req  wx/eddf`), `core/src/scenario/pilot.ts`.
- **`wait: { reply: { options, timeout_min, default } }`**: the options are single `A–Z0–9` words, `default` is required and is one of `options`. A reply is a pilot message whose first word is an option (with several pending waits — the earliest started); the remaining words are `reply.arg`. With no reply within `timeout_min` of **flight** time (like `wait.minutes`: a pause does not count, ×N speeds it up), `default` is taken and `reply.timeout = true`. A reply to a question takes priority over a command with the same word (`DIVERT`). The `REPLY_EXPECTED` event — the app asks the transport to poll more often (`expectReply`, ≤ 3 min for Hoppie), `REPLY_TIMEOUT` — goes to the feed.
- **`branch: { OPTION: [steps], … }`** — by the last reply (`reply.option`); a reply without a branch — continue after `branch`. Branches are nested; keys are checked against the nearest `wait: reply`; a `branch` after branching where the branches asked different questions, without a new question, is a load error. It compiles to a flat program with jumps — the run state is still the step number (serialised).
- **`wait: { until: "<condition>", timeout_min }`** (T39): the condition is in the `conditions` language, checked on entering the step (already true — no need to wait) and on every tick; not checked while telemetry is lost. `timeout_min` is **flight** time, like `reply`: a pause does not count, ×N speeds it up. The outcome is `MET` (the condition was met; on the same tick it beats the timeout) or `TIMEOUT`; it is stored in `reply.option` (`reply.timeout = true` on `TIMEOUT`), so the following `branch` splits into `MET` / `TIMEOUT` branches (other keys are a load error, as with `reply`). The wait state is `run.until = { step, deadlineMs }`, serialised; old-format states are readable. The `WAIT_UNTIL {id, result}` event goes to the replay log.
- **Random values and loops (T50).**
  - `draw: [{ weight?, set: { run.<name>: value | [min, max] } }, …]` — picks a variant by weight (integer 1..1000, default 1) and gives the run `run.<name>` values; `[min, max]` is a uniform integer. The roll comes from the scenario's seeded `Rng` at the moment of the step, the values live in the run state (determinism and serialisation). A name that the chosen variant lacks is `null`. `run.*` is readable by conditions and templates.
  - `loop: { until, stop?, every_min?, steps }` — repeats `steps`; `until` (outcome `MET`) and `stop` (outcome `STOP`) are checked on every tick, including during a wait inside the loop (it is reset), and on entry/return. The outcome is in `reply.option`; the following `branch` may have `MET` / `STOP` branches and the replies of the loop body. `loop.min` is flight minutes since entering the loop. There must be a wait inside the loop (otherwise a load error); no nested loops. `break: true` exits the loop with the last reply.
  - `wait: { reply: { options, timeout_round: true, default } }` (only in a loop with `every_min`) — the timeout is not after N minutes but at the nearest round boundary `entry + k × every_min` of flight time: a pilot reply within a round does not shift the grid. `reply.timeout = true` when the round has ended.
  - `if: "<condition>", steps: [steps]` — the steps run only if the condition is true at the moment of the step; `break` inside exits the loop.
  - The template `{flight.now|plusmin:20|hhmm}` — the time in 20 minutes. Variables `flight.holding` (a hold announced by a scenario, `set: flight.hold`) and `flight.hold_fuel_low` (fuel has reached `alternate_burn + reserve` + 10 %; without a fuel reading — the OFP cruise average-burn reserve `extra + contingency` is used up; `false` outside a hold).
  - Scenarios: `drone_activity` (30 min – 3 h), `dest_fire` (20 min – 2 h), `runway_closure_dest` (30–60 min for the reasons FOD/BIRD STRIKE, 60–180 min DISABLED ACFT, in 3 of 30 cases — closed until cancelled: diversion at the first update). An update every 20 min with a new time (XATC sends a new UM93 at every update); the all-clear comes when the drawn time has run out, not on the grid; the loop stops when `flight.divert != null` and on landing. `hold_fuel_watch` — "MIN DIVERSION FUEL" (reply DIVERT / STAY, no reply in 5 min — DIVERT).
- **`resend: { of: [id, …] }`** — repeats the last message of one of this flight's scenarios (verbatim). The variable `flight.sent` is the ids of scenarios that have already sent something (`'final_loadsheet' in flight.sent`).
- **Pilot commands** — trigger `on: command`, `command: REQ_WX | REQ_GATE | REQ_LOADSHEET | DELAY | DIVERT | ETA | HELP | MEDICAL | REQ_ATIS | RDY | REQ_GATE_CHANGE | REQ_NOTAM` (cooldown defaults to `none`: answer every one). Syntax: `REQ WX [ICAO]` (`REQ METAR`; without an airport — the destination), `REQ GATE`, `REQ LOADSHEET` (`REQ LS`), `DELAY <1–600> [reason]`, `DIVERT <ICAO>`, `ETA`, `HELP`; **T44:** `MEDICAL [text]` (airborne only), `REQ ATIS [ICAO]`, `RDY` (before OUT), `REQ GATE CHANGE [gate] [reason]` (before IN); extra words are ignored. Additional T44 run variables: `cmd.atis`, `cmd.atis_code`, `cmd.gate`, `cmd.new_gate`, `cmd.divert_nm`, `cmd.divert_eta` (distance and ETA — only for airports from the OFP at GS ≥ 60 kt). Run variables: `cmd.name`, `cmd.text`, `cmd.icao`, `cmd.minutes`, `cmd.reason`, `cmd.metar` (the OFP METAR for departure/destination/alternates, otherwise null — before T13). Part of a command is done by the core (deterministically, before the scenarios): `DELAY` before OUT is added to the flight delay — like a late start (`est_*`, `sched_*`/`est_*` triggers, `flight.delay_min`; already sent messages are not repeated); `DIVERT` only airborne (OFF yes, ON no) and not to the destination — `flight.divert`. The arrival scenarios of the base set (`dest_weather`, `landing_data`, `gate_assignment`, `arrival_info`, `welcome_turnaround`) do not run on a diversion; rerouting to the alternate is not done.
- **Company NOTAM summary (T95).** NOTAMs from the OFP (`Ofp.notams`, docs/06 "SimBrief") are selected by `packages/core/src/ext/notam.ts`: by Q-code (FAA JO 7930.2U, App. B) — importance groups `FA`; `MR MT MD`; `IC IG IL ID IS IT IU GA`; `PI PU PM PA`; `LA LP LV LR LE LC LZ LH`; `MN MP MK`, without "back to normal" states (`AK AO AF CC HV CN AX`) and without NOTAMs lacking a Q-code; in force in the ETA ± 60 min window (ETA = OFF + the planned time en route, before OFF — `est_on` + delay; for departure before OFF — `est_out` + delay); up to 5 per airport. An item: `<number> TIL DDHHMMZ[ EST]` or `PERM`, the text of field E up to 48 characters by words, `SKED <field D>` as is (up to 48 characters; not parsed). Variables: `ofp.notam_dest`, `ofp.notam_altn` (items or `NIL SIGNIFICANT`; without an alternate — null), `ofp.notam_count`, `ofp.release` (OFP release time, ms). The scenario `base/company_notam` — 200 NM before TOD (next to `dest_weather`), only if items > 0. The command `REQ NOTAM [ICAO]` (without ICAO — the destination): `cmd.notam` — the airport summary from the OFP (departure, destination, alternates) or `NIL SIGNIFICANT`, for others — null (`NO NOTAM DATA`), scenario `commands/cmd_req_notam`. NOTAMs shift together with the OFP date (`alignOfpDay`).
- **Every command gets a reply.** An unknown one — `UNABLE <text> / SEND HELP FOR LIST`; a known one with wrong arguments or impossible to carry out — `UNABLE <COMMAND> / <why or format>`; a known one but without an enabled scenario — `RCVD <text>`. These are messages of the core itself (`scenarioId: '#ops'`), through the formatter.
- Handlers — `packages/scenarios/commands/*.yaml` (11 files: `cmd_help`, `cmd_req_wx`(+`_no_data`), `cmd_req_gate`(+`_divert`), `cmd_req_loadsheet`(+`_none`), `cmd_delay`, `cmd_divert` — with a question about the reason and branches, `cmd_eta`, `cmd_eta_ground`). Variants of one command are told apart by conditions. The app and `pnpm replay` load them together with the base set; in the settings they are disabled like ordinary scenarios.
- A new template formatter `or:TEXT` — text instead of `----` for an empty value (`{cmd.reason|or:NOT GIVEN}`).
- Flight recording: the `tick` line got an optional field `inbound`; `pnpm replay run … --pilot "<min>=<text>"` adds pilot messages to a run.
- Tests: `core/test/two-way.test.ts` (parser, reply/branch/timeout/nesting, serialisation in the middle of a question, telemetry loss, commands), `scenarios/test/commands.test.ts` (all commands on 3 synthetic flights × 3 profiles, a whole conversation, the reference `reference/scenarios/medical_onboard.yaml` without `set`/`calc.*`).
- **Random start within a phase and an airport in the reply (T51).** `trigger: { on: phase, phase: CRUISE, window: { after_min: 10, before_tod_min: 30 } }` — the scenario does not start on the edge but is deferred to a random moment: after the `probability` roll from the seed, a fraction of the path `f` is taken, and the start is at `flight.minutes_to_tod ≤ T0 − after_min − f × (T0 − after_min − before_tod_min)` (T0 is the value on the edge): uniformly along the path; pauses and ×N do not shift it. At the start moment the conditions, cooldown and excludes are checked again; "run now" goes without the window. The reply `DIVERT <ICAO> …`: `reply.icao` is the airport, if the core knows it (OFP, the T50 reserve, found by the app in `airports.csv` — the core sends a `DATA_REQUEST` `place` and waits `dataWaitMs`; not the destination, airborne only), the rest is `reply.arg`; `reply.unknown` — `ZZZZ`. Templates: `{a|else:b.c}` — another variable instead of an empty one; a line starting with `~` is skipped if it contains an empty value. `flight.divert_nm` — the distance to the diversion airport, if its coordinates are known.

## Interval between messages

- `CoreOptions.minGapMs` (default 0): telexes leave the core no more often than one per interval by the clock (`Clock`); the others wait in the core queue (`CoreState.outbox`, serialised) and go out at their release time. Replies to the pilot (everything sent while handling their message: a reply to a question, commands, `UNABLE`/`RCVD`; the field `toPilot`) go ahead of the others in the queue. Reason: aircraft poll Hoppie about once a minute, and close messages arrived in a batch (human check 2026-10-08). In the app — the "Gap between messages" setting (60 s by default, 0 — immediately), written to the recording header (`header.minGapMs`), applied by replay; the network status shows "waiting for the interval: N".

## Behaviour after app downtime (T64)

While the app is closed, the core does not tick. After recovery (docs/03) the first tick arrives with a gap: the FSM sees `TELEMETRY_LOST` / `TELEMETRY_RESTORED` and, if the aircraft has moved, `DISCONTINUITY` (docs/04). Flight time does not run across the gap, so `wait: { minutes }`, waiting for a reply and `wait: until` continue from the same place. Clock-based triggers (`on: time`: `sched_*`, `est_*`, `out/off/on/in` + N) whose time came during the downtime fire on the first tick after recovery, in order, spaced by `minGapMs` (user decision 2026-10-29: send in order, discard nothing); scenario conditions (`phase in …`) are checked as usual. There is no separate core input for recovery: a recording with downtime is replayed by `pnpm replay run` the same way as it went live.

## External data (T13)

- **The core does not go to the network** (invariant 3). Data is a core input `CoreInput.data: ExtDataUpdate` (`core/src/ext/data.ts`): `wx` (METAR/TAF by airport, `null` = no report), `atc` (VATSIM stations of the departure and destination airports), `events` (EONET), `stands` (OSM stands at the destination). Each field replaces the previous one; the data is kept in the engine state (`ext`, serialised) and written to the flight recording (`tick.data`), so replay is deterministic.
- **Variables**: `wx.{orig,dest,altn}_metar` — live METAR, otherwise from the OFP; `_live` — whether it is live; `_obs` — observation time; `_taf` — live only. Live = not older than 3 h. `ext.{orig,dest}_atc` — lines `CALLSIGN FREQUENCY` (ATIS, DEL, GND, TWR, APP), `_atc_count` (null without data or if the VATSIM data is older than 20 min), `ext.dest_atis` — the ATIS letter. `ext.event_*` — the nearest EONET event **ahead along the route** within 150 NM of it: `id`, `title`, `category` (`SEVERE STORM`, `WILDFIRE`, `VOLCANO`…), `ahead_nm` (along the route from the aircraft), `off_nm` (from the route). The position of an event relative to the route is computed once on receipt (the OFP polyline with a step ≤ 10 NM).
- **Gate from OSM**: with stands at the destination, `ops.arr_gate` is taken from them (gates if there are ≥ 3, otherwise stands; natural order; one Rng draw `<seed>/#stands`). Once a message with `ops.arr_gate` has gone out, new stands are ignored (`ext.gateLocked`) — the gate in `gate_assignment`, `REQ GATE`, `arrival_info` is the same.
- **`REQ WX` with a data request**: with `dataWaitMs > 0` (the app with live data — 60 s) and without fresh (≤ 15 min) airport weather, the core defers the command and emits the event `DATA_REQUEST {kind: wx, icao}`; the reply comes when the data arrives or the time runs out (then with what there is: the OFP METAR or "no data"). Variables: `cmd.metar` (live or from the OFP), `cmd.taf`, `cmd.wx_live`, `cmd.wx_obs`. Without a data source (`dataWaitMs = 0`, the default) — an immediate reply.
- **Scenarios**: `packages/scenarios/external/` — `dest_weather_live` (instead of `dest_weather`, if the destination has a live METAR; `dest_weather` got the condition `!wx.dest_live`), `vatsim_atc` / `vatsim_atc_none` (80 NM before TOD; without VATSIM data — nothing), `natural_event` (in cruise, an event ≤ 250 NM ahead, no later than 15 min before TOD), `space_launch` / `space_launch_done` (T28: a rocket launch, see below). `commands/cmd_req_wx_live` (METAR + TAF), `cmd_req_wx` — only without live weather. `takeoff_data` takes `wx.orig_metar`. The app and `pnpm replay` load `external/` together with `base/` and `commands/`.
- **Adapters** — the package `@acars/data-sources` (see `06`). Tests: `core/test/ext-data.test.ts`, `scenarios/test/external.test.ts` (each scenario on 3 flights × 3 profiles with and without data; the whole set with data), `data-sources/test/adapters.test.ts`, `desktop/test/controller.test.ts` ("live data").

The scenario starts on this tick without a trigger, probability, cooldown and `excludes`, but **only if its conditions are met** (phase, delay, flags — otherwise the messages would be meaningless) and it is not running now. The result is a `FORCED {id, result: started | conditions | running | unknown, detail}` event (for `conditions` — the text of the unmet condition), `forced_*` in the app feed. While telemetry is lost, the request waits in the core state (`forced`). Flight recording: the `force` field of the `tick` line, replay reproduces it.

## VDGS display (T22)

- **`vdgs: { narrow: [lines], wide?, x?, flex?, small?, duration_sec? }`** — text on the GSX VDGS display at the arrival airport (or the diversion airport). A line is a template or `{ red: template }`. Limits: small 4×2, narrow 6×5, wide 9×6, x 10×6, flex 10×5 (SafeDock FLEX, since 2026-11-05) — the last line of the narrow/wide/x display is taken by the GSX scrolling line (`core/src/sim/vdgs.ts`, source — `06`, "GSX VDGS"). `narrow` is required, `wide`/`x`/`flex` without their own lines take `narrow`, `small` — only if set. Characters A–Z, 0–9, space, `- / . :`; lower case is converted to upper. A literal that does not fit is a load error; a template — `SCENARIO_ERROR` at run time, without abbreviation. `duration_sec` 1–60, default 6.
- The core output is a `vdgs` command in `CoreOutput.commands` (the type from T21), not a telex: it does not go through Hoppie and the aircraft display formatter, and does not wait for `minGapMs`. The app writes it to a GSX file, one message per scenario (a new one replaces the old). In the flight recording — a `cmd` line.
- **T102:** `at: orig | dest` (default `dest` — arrival or diversion; `orig` — the departure stand), `replaces: flight_information` — the message gets the `id` of the standard GSX message and replaces it (in the recording and in the file, one message per scenario). An empty string `""` is an empty display line. `vdgs: stop` — remove the scenario's message (a `vdgs` command with `vdgs: null`; in the recording `data: {"action":"stop"}`; when the last one is removed, the file is deleted). The app does not rewrite the file if the text has not changed.
- T102 variables: `flight.tobt` — the airline TOBT = `sched_out` + the delay without the ATFM slot (late start, pilot `DELAY`, `set: flight.delay_min` of all scenarios except `slot_ctot`; core state `tobtDelayMs`), `flight.minutes_to_tobt` — minutes to TOBT rounded up (0 from the TOBT moment, negative afterwards), `ofp.orig_acdm` — the departure airport has implemented A-CDM (`core/src/ext/acdm-airports.ts`, 35 EUROCONTROL airports).
- The set — `packages/scenarios/sim/`: `vdgs_arrival` (after landing: airline, flight, departure airport, gate), `vdgs_divert`, `vdgs_departure` (T102: at the departure stand at an A-CDM airport, replacing `flight_information` — flight, destination, runway, SID; from TOBT − 30 min — TOBT and `TTD nnMIN`; from TOBT — empty; 15 min after TOBT without OUT — red `FLIGHT SUSPENDED / NEW TOBT REQUIRED`, narrow `FLIGHT/SUSPND/NEW/TOBT/REQRD`; a new `DELAY` brings the TOBT back; rewritten once a minute of flight time, at OUT — `vdgs: stop`; the trigger `est_out − 180` — not `sched_out − N`: it is not compressed by a late start and does not take part in its calculation, so the display is there from the first tick and the timing of the other messages does not change), `vdgs_departure_etd` (T103, **disabled by default**, not a reproduction of a real display: at airports not in the A-CDM table — the same display, but ETD = `ofp.est_out` with all delays, including the slot, and `TTD`; the variable `flight.minutes_to_etd`; without FLIGHT SUSPENDED).
- Tests: `core/test/vdgs.test.ts`, `scenarios/test/sim.test.ts`, `apps/desktop/test/vdgs.test.ts`.

## Aircraft type (T40)

- **The type-code table has not been checked against ICAO Doc 8643** (there was no data export; user decision 2026-10-14) — `[VERIFY]` on real OFPs. Hold compartment names and ULD kinds are from the Airbus AC (A320 Rev. 44, A330 Rev. 32) and the Boeing ACAPS 737NG (Rev C); they contain no ULD position codes, so position numbers are not generated. Seat letters are an assumption (the layout depends on the airline).

### T43/T44: gate, slot, fuel (2026-10-14)

- **The gate is not invented.** `ops.arr_gate` = `null` until there are real OSM stands. For texts: `ops.gate_known`, `ops.gate_place` (`GATE A12` / `STAND 12` / `GATE TBA`), `ops.gate_line` (`… CONFIRMED` / `GATE WILL BE ADVISED`), `ops.gate_expected`, `ops.ground_support` (`GPU AND PCA AVBL` for a gate, `REMOTE STAND, BUS AND STAIRS` for a stand without `aeroway=gate`, `GROUND SUPPORT TBA`). Without stands, `gate_assignment`, `gate_reassignment` and VDGS do not run. `irr.new_gate` = `null` if there is no other stand.
- **Slot.** `slot_ctot` sets `set: flight.delay_min` (the delay is not below N minutes, before OUT only); the CTOT announced by the slot is not shifted by the delay the slot itself caused (`delayRaisedMs`). `slot_missed` — takeoff later than CTOT + 10 min (window −5/+10, Irish AIP ENR 1.9 of 18.05.2023); it does not invent a new CTOT. `RDY` — the window EOBT−15 min … CTOT−taxi, an improvement chance of 40 %, a gain of 5–15 min (assumptions).
- **T46.** `flight.touchdown_fpm` — the descent rate at touchdown, ft/min: the engine reads the telemetry `touchdownFpm` once, when ON is recorded (the SimVar `PLANE TOUCHDOWN NORMAL VELOCITY` holds the value of the previous landing, so it cannot be trusted earlier); `null` without the field or with zero. `flight.fuel_below_plan_kg` — the planned fuel on board at this point of the route (`OfpFix.planFobKg`, interpolation by distance flown, no extrapolation) minus the actual, kg (plus — below plan), airborne only; `flight.fuel_plan_tol_kg` — the tolerance at this point (5 % of plan, not less than 500 kg). No plan in the OFP or no telemetry — `null`. Scenarios: `hard_landing_check` (ON_BLOCK, > 350 ft/min, CONFIRM → flags `hardland_reg/date`, lifetime 3 days), `hard_landing_followup`, `fuel_monitoring` (CRUISE, `wait: until` up to 12 h, replies WX/ATC/LEAK/NORMAL), `ped_fire_cabin` (0.5 % per flight — changeable in the app, like the other irregular ones).
- **T94 (FDM).** The core option `fdm` (the app enables it and writes `fdm: true` to the recording header; without the field — off, recordings before T94 play as before): `FdmMonitor` (`core/src/fdm/monitor.ts`) finds events from telemetry — `sink_rate` (VS steeper than −1000 ft/min for ≥ 5 s in a row from 1000 to 50 ft above the destination aerodrome), `gear_up` and `flaps` at 1000 ft above the aerodrome (flaps less than at touchdown), `speed` (IAS > 255 kt for ≥ 15 s below 10 000 ft MSL, one in the climb and one in the descent), `go_around` below 1000 ft (information). The approach height is `altFt − the OFP destination aerodrome elevation`; on pause and on a telemetry gap > 5 s the series is broken; one event of each kind per approach, the worst value. Variables: `fdm.count` (`null` — FDM off), `fdm.line1`…`fdm.line8` (`1 SINK RATE 1400 FPM AT 800 FT 1018Z`, by time), `fdm.more`. The scenario `base/fdm_letter` (ON_BLOCK + 3 min, `SAFETY DEPT FDM`, replies ACK / REPORT); events are in the flight summary (`FlightReport.fdm`) and the flight log.
- **Fuel.** `fuel_slip`: trigger STD−18, waits for `flight.fuel_stable` (after refuelling the fuel did not change by more than 100 kg for a minute) until STD−12; `flight.fuel_uplift_kg`, `flight.fuel_diff_kg`.
- **GSX (T98, `packages/core/src/scenario/ground.ts`).** The bridge reads the GSX Pro service states into the telemetry field `ground` (docs/03). GSX is **active** from the first sample where a service is requested, in progress or completed (4–6) or baggage loading is under way (assumption D1, approved 2026-11-07); without that — the former time-based logic. Variables: `ground.active`; `ground.boarding`, `ground.deboarding`, `ground.refuel`, `ground.catering`, `ground.departure` — the last state as a word (`available`, `unavailable`, `bypassed`, `requested`, `performing`, `completed`; `null` without GSX); `ground.cargo`; `ground.boarding_done`, `ground.refuel_done` — this flight's service is done (after GSX became active); `ground.refuel_busy` — refuelling is requested or in progress. Engine events `GSX_BOARDING_DONE`, `GSX_REFUEL_DONE` (once per flight, `trigger: { on: event }`; in the core output — the `GROUND` event, in the replay report — `GSX`). The state (`ground`) is part of the engine state; the `ground` field is part of the recorded telemetry, and replay reproduces it. Scenarios: `final_loadsheet` — if GSX is active and boarding is not done, it waits for `ground.boarding_done` for up to 10 min (a game number, user decision 2026-11-07: a timeout, then by schedule), then 1 min (after `BOARDING COMPLETED`) and further as without GSX; `fuel_slip` — while `ground.refuel_busy`, it waits for the end of refuelling for up to 10 min (the same number, extended to the receipt), then the former wait for `flight.fuel_stable`; `boarding_completed` (new, `base/`, passenger kinds) — on `GSX_BOARDING_DONE`: `PAX` = `load.pax` (the OFP with LMC, not the GSX count — D3). Without GSX the `if` steps do not run — flights and old recordings without the field give the former messages and events. A delay code for boarding lateness (item 4 of the card) is not done (user decision 2026-11-07).
- **Connection.** `irr.connect_flight` = `ONWARD FLT` if the flight's airline operated its own departures from the destination airport per OpenFlights (`ext/airline.ts`, 2014 data; no flight number), otherwise `null` — `short_connection` (and with it `connection_*`) does not run. The STD of the connection after STA — by `ofp.airline_type` (`ext/airline.ts`): low-cost 50–70 min, hub carrier 100–140, others 50–95; the turnaround `ops.turnaround_min` — 45–55 / 105–135 / 50–70 (heavies 75–95). The test hook `syntheticConnections` enables a synthetic flight with a number. **T30:** with the user's AeroDataBox key, a real departure of the airline (`CoreInput.data.connex`, below) replaces both `ONWARD FLT` and the synthetic flight: `irr.connect_flight` — the number (`JX862`), `irr.connect_std` and `_margin_min`/`_left_min` — from its STD; `irr.connect_dest` — where it flies, `irr.connect_gate` — the gate, otherwise `TERM <terminal>`, otherwise null; `irr.connect_src` — `SRC AERODATABOX` (the last line of `short_connection`/`connection_*`, attribution by conditions), without a real flight — an empty string (the formatter removes an empty last line). `irr.connect_pax` stays synthetic (C7). **T55** (`nextLegVersion: 3`): "there are departures from the destination airport" — yes, if `connex` has an operating departure of the company or `routes` has a route with it; otherwise OpenFlights, as before.
- **TLR and OFP crew.** `ofp.to_flaps`, `ofp.to_thrust` (`FLEX 71` / `TOGA`), `ofp.v1|vr|v2`, `ofp.ldg_flaps`, `ofp.vref` — from the SimBrief TLR, only if the TLR is computed for the runway per the OFP plan (otherwise `null`); `ofp.crew_cockpit`, `ofp.crew_cabin` — the headcount from the OFP `crew`. `takeoff_data` / `landing_data` add the lines `FLAPS … V1 … VR … V2 …` / `FLAPS … VREF …`, `final_loadsheet` — `CREW 2/16` and `OEW`; `ops.cabin_crew` — from the OFP, if present. Without TLR / crew — the former text at the trigger moment (the "if" branch MET), with them — a tick later (TIMEOUT). Recordings before T43 without these fields read as `null`.
- **Names (`{name:crew}`, `{name:ops}`), version 2.** `names.region` — by the airline's country (OpenFlights), otherwise the departure airport's country (VATSpy), otherwise `null` (ICAO prefix, as in version 1); `names.mix` — `some` (every tenth name from another region) or `all` (UAE, ETD, QTR: any region). The core option `namesVersion` (1/2, default 2) is written to the recording header; replay without the field — version 1.
- **Delay codes.** `flight.delay_codes` — the `DL` element of the MVT (`DL81/63/0025/0010`) after OUT later than STD, otherwise `null`; the delay parts are `delayParts` in the engine state (late start `63`, slot `81`, pilot `DELAY` — a code from the reason), `core/src/scenario/delay-codes.ts`. `departure_report` / `block_report` add the line last.
- **Diversion.** `divert_arrival` at ON_BLOCK and the `recovery_*` flags (3 days, `flags-expiry.ts`) → `recovery_followup` on the next flight from this airport.
