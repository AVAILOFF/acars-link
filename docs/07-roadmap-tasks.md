## Этап 5 — Функции уровня RealAcars / RealAcars Plus

Решение пользователя 2026-10-09: реализовать функции оригинала (бесплатного RealAcars и анонсов RealAcars Plus), которых у нас нет. Код оригинала не копируется (инвариант 1), только идеи из публичных описаний.

### Правило реализма и проверки данных (для всех карточек этапа 5)

1. **Максимальный реализм.** Формат, фразеология, тайминги и логика — как в реальной эксплуатации. Образцы сообщений берутся из реальных источников (ICAO Doc 4444 и набор сообщений CPDLC, ARINC 620/623, AIP, реальные распечатки ACARS). Источник образца указывается в комментарии к сценарию или таблице.
2. **Максимальная проверка данных.** Коды, частоты, правила эшелонов, диапазоны сквоков, границы FIR, станции, спутники, расписания, поля API — только из проверенного источника. В `06-integrations.md` (или рядом с таблицей) записываются источник, дата сверки и лицензия. Не угадывать: место без источника помечается `[ПРОВЕРИТЬ]` и проверяется до использования.
3. **Допущения — только с одобрением.** Упрощение, приближение, эвристика или синтетические данные разрешены, но **до реализации** их нужно перечислить пользователю: что допускаем, почему нет реальных данных, чем это отличается от реальности, заметит ли пилот. Без явного «да» допущение не реализуется. Одобренные допущения записываются в карточку (подраздел «Допущения») с датой.
4. **Таблицы под тестами.** Каждая таблица правил (запрещённые сквоки, эшелоны, диапазоны) покрыта тестами на реальных примерах. Ответы внешних API — урезанные реальные фикстуры. Внешние данные попадают в запись полёта (replay детерминирован).
5. **`[ПРИ РЕЛИЗЕ]`** (решение пользователя 2026-10-09): вопрос, который не требует проверки человеком в симуляторе и не мешает личному использованию (лицензии, недоступные AIP, реальные OFP для сверки), закрыт до публичного релиза. Сейчас действует принятое решение или допущение. Сводный список — `08`, «Отложено до публичного релиза». Пометка `[ПРОВЕРИТЬ]` человеком в симуляторе остаётся открытой.
6. Инварианты не ослабляются: числа не от LLM (8), всё через форматтер (9), ключи только у пользователя или на бэкенде (2), уважение к сети Hoppie (6).

### Приоритет 1

#### T21 — Канал команд «приложение → мост»
Протокол моста v2: кроме телеметрии, приложение отправляет команды (белый список типов, валидация, подтверждение или ошибка). Слушает только 127.0.0.1. Ядро выдаёт новый тип выхода «команда симулятору», рядом с «отправить сообщение». Это основа для T22 и T34.
**Готово, когда:** fake-источник принимает и подтверждает команды, тесты протокола в `bridge:test` и в `apps/desktop/test` зелёные, v1-клиенты не ломаются.

#### T22 — Свои сообщения на VDGS через GSX
Вывод текста от авиакомпании на табло VDGS (гейт, номер рейса, приветствие, сообщения сценариев: новый шаг `vdgs:`). По документации FSDreamTeam: механизм (L-переменные, файл или API GSX Pro), длина и набор символов, версия GSX (закрыто анализом 2026-10-09, ниже; набор символов — проверка человеком). Без GSX функция молча выключена. Зависит от T21.
**Проверка человеком:** MSFS 2024 + GSX Pro, аэропорт с VDGS от GSX, прилёт на стоянку: текст появляется на табло, не мешает парковке.

**Анализ (2026-10-09).** Источник — руководство FSDreamTeam «VGDS Custom Messages System» от 2025-07-29, оно поставляется с GSX Pro (`couatl\GSX\SDK\Samples\VGDS\vgds_developer_manual.pdf`), подробно в `06`, «GSX VDGS». Механизм — JSON-файлы в `%APPDATA%\Virtuali\GSX\VGDS\`, GSX перечитывает их сам. L-переменных и API нет, мост не нужен. Лимиты: small 4×2 (на стоянке), narrow 6×6, wide 9×7, x 10×7. Набор символов в источнике не описан. Когда GSX показывает сообщение и не перебивает ли оно указания по парковке — тоже не описано, это проверка человеком.

**Решение пользователя (2026-10-09):** файл пишет main-процесс приложения (`apps/desktop/src/main/vdgs.ts`), не мост. От T21 используется только тип выхода ядра `CoreOutput.commands` (команда `vdgs`).

**Допущения (одобрены пользователем 2026-10-09):**
1. Сообщение фильтруется только по аэропорту прилёта (или диверсии), без фильтра по гейту: имена гейтов OFP/OSM/`ops.arr_gate` могут не совпасть с `gate_name`/`gate_number` GSX.
2. `valid_from`/`valid_until` не используются (время симулятора может отличаться от реального). Приложение владеет одним файлом `acars-sim.json`, пишет его атомарно и удаляет в конце рейса, при выходе и при запуске приложения.
3. GSX считается установленным, если есть папка `%APPDATA%\Virtuali\GSX`. Нет папки — функция молча выключена.
4. Шаг `vdgs:`: `narrow` обязателен, `wide` и `x` без своих строк берут `narrow`, `small` выводится, только если задан. Строка, которая не помещается, — ошибка (литерал — при загрузке сценария, шаблон — `SCENARIO_ERROR` при выполнении), без сокращений.
5. Символы: только A–Z, 0–9, пробел и `- / . :`. Значения (рейс, гейт, аэропорт) подставляет ядро. Переменные SimBrief самого GSX не используются (инвариант 8).

#### T23 — ROPS: станция, CPDLC-логон, учёт FIR
Имитация станции УВД через Hoppie: логон пилота на станцию, ответ с текущим органом УВД. При пересечении границы FIR сообщение о логоне обновляется (передача связи, как CDA/NDA в реальном CPDLC). Границы FIR — внешние данные во входе ядра, проверка «точка в полигоне» в ядре.
**Открытые вопросы (до кода; закрыты решениями 2026-10-09 ниже, лицензия VATSpy — CC BY-SA 4.0):** позывной станции на общей сети Hoppie (уникальный на пользователя? правила Hoppie `[ПРОВЕРИТЬ]`, согласование с Hoppie из `02`); тип пакета `cpdlc` или `telex`; какие самолёты поддерживают CPDLC через Hoppie; поведение, когда на VATSIM онлайн живой диспетчер этого сектора (не конфликтовать). Источник границ FIR (VATSpy data project или другой) — лицензия `[ПРОВЕРИТЬ]`.
**Проверка человеком:** FBW A32NX и PMDG 777, логон на станцию, полёт через 2+ FIR: сообщения приходят на границах.

**Анализ (2026-10-09).** Подробно — `06`, «CPDLC через Hoppie» и «Границы FIR». Правил о позывных станций у Hoppie нет. Живые станции VATSIM заходят под 4-буквенными кодами (EDGG, EDYJ, LONC). Логон и передача связи у Hoppie — только пакеты `cpdlc` (`/data2/<min>/<mrn>/<ra>/<text>`), telex самолёты так не обрабатывают. Фразы взяты из кода FBW A32NX и перехваченных пакетов сети: `REQUEST LOGON` → `LOGON ACCEPTED`, `CURRENT ATC UNIT@_@<код>@_@<имя> CTL`, `HANDOVER @<код>`, `LOGOFF`. Границы FIR — VATSpy Data Project (CC BY-SA 4.0). Какие самолёты поддерживают CPDLC через Hoppie: FBW A32NX (по коду). iniBuilds A350/A380 шлют `REQUEST LOGON` (проверено в T09). Остальные — проверка человеком.

**Решения пользователя (2026-10-09):**
1. Позывной станции — `X` + три последние буквы FIR (EDGG → XDGG). Индексов ИКАО на X нет: станция не перехватывает логоны чужих пилотов и не мешает живым диспетчерам. На границе FIR — настоящая передача связи (`HANDOVER @XDWW`), самолёт сам логинится на следующую станцию.
2. Пакеты УВД — `cpdlc`, сообщения авиакомпании остаются `telex`. Для текста CPDLC в форматтере свой профиль: без `/` (FBW читает текст как шестое поле через `/`), `@` и `_` разрешены.
3. Если на VATSIM онлайн центр (CTR/FSS), покрывающий FIR, станция уступает: подключённому самолёту — уведомление `VATSIM ATC ONLINE@_@CONTACT <позывной> @<частота>@` и `LOGOFF`, на логон — `UNABLE` с тем же текстом. В следующей FIR или после ухода диспетчера станция снова принимает логон. Настройка «Уступать живым диспетчерам VATSIM», по умолчанию включена.

**Допущения (одобрены пользователем 2026-10-09):**
1. Границы FIR — из VATSpy `Boundaries.geojson` (данные VATSIM, приближение реальных FIR). Файл скачивается приложением и кэшируется на 7 дней, в репозитории только урезанная фикстура для тестов.
2. Только FIR (4-буквенные области VATSpy), без UIR и секторов. Где области перекрываются, первыми идут области, которые служат FIR какого-нибудь аэропорта (`[Airports]` VATSpy.dat): накладные области без аэропортов (`EGVV` Swanwick Military, `EDXX` FIS only) не перекрывают FIR. Среди оставшихся выбирается большая (London TMA `EGTL` внутри `EGTT`). В Австралии у VATSpy только секторы (YGUN «Melbourne (Gundagai)»), станция там — по сектору.
3. Логон принимается в любой FIR. Реальное покрытие CPDLC (в Европе — только выше FL285 и т. п.) не моделируется.

**Реализация.** Ядро: `packages/core/src/atc/` (`cpdlc.ts` — пакеты и профиль, `fir.ts` — точка в полигоне, позывной и имя органа, `rops.ts` — станция). Опция ядра `rops: { enabled, standAside }`, выход `CoreOutput.listen` — позывные станций, которые транспорт опрашивает до первой отправки (станция ждёт логона). Входящие с `to` = станция `X…` идут в станцию, остальные — авиакомпании. Сообщения УВД не ждут интервала между telex. Данные: `packages/data-sources/src/vatspy.ts` (FIR вдоль маршрута, центры VATSIM по префиксам VATSpy, включая UIR). Приложение: настройка «Станция УВД ROPS» (по умолчанию выключена, нужны живые данные), строка ROPS в статусе, события в ленте. Прочие запросы CPDLC до T25 получают `MESSAGE NOT SUPPORTED BY THIS ATS UNIT` (фраза живых станций Hoppie). На стоянке (ON_BLOCK) станция шлёт `LOGOFF` подключённому самолёту и перестаёт опрашиваться.

#### T24 — ROPS: PDC по запросу, сквок по региональным правилам
Запрос PDC (DCL) от пилота, ответ в реальном формате (ARINC 623 / ED-85A, американский PDC — `[ПРОВЕРИТЬ]` образцы): ВПП, SID, начальная высота, частота вылета, ATIS, сквок. Сквок — по региональным правилам (ORCAM и аналоги), с банлистом: аварийные и специальные коды по ICAO Annex 10 Vol IV, Doc 4444 и региональным AIP (7500/7600/7700, 2000, 7000, 1200, 1000, 7400 и т. д. — полный список только из источников). Данные, которых нет в OFP (начальная высота, частота), — только из источника или как одобренное допущение.
**Готово, когда:** тесты банлиста и диапазонов по регионам на реальных примерах; PDC для 3+ регионов (EU, US, Азия) совпадает с реальными образцами по формату.

**Анализ (2026-10-09).** Подробно — `06`, «DCL/PDC» и «Таблицы сквоков». Запрос пилота в Hoppie — telex `REQUEST PREDEP CLEARANCE <позывной> <тип> TO <назн.> AT <вылет> STAND <x> ATIS <буква>` (FBW `DclMessage.ts`, TopSky «RCD»). Европа и Азия — ARINC 623 DCL (RCD → FSM → CLD → CDA/WILCO → FSM). Образцы: AIP Сингапура eSUP 2018/013, AIP Малайзии SUP 02/25 и реальные DCL, расшифрованные из эфира ACARS (EDDF 2022/2023, EFHK/EGLL/LSZH 2025, WSSS/VHHH/VTBS/RKSI 2023). Официального европейского AIP с образцом не нашлось, поэтому для Европы — реальные DCL и руководство TopSky. США — PDC через хост авиакомпании, без ответа пилота: поля по FAA JO 7110.113F, раскладка — реальный PDC Delta (KMSP, 2025-12-29). Таблицы сквоков: EUROCONTROL CAL v4.13, FAA JO 7110.66H (NBCAP), ICAO APAC eANP Vol II (Table ATM II-APAC-2). Реальные сквоки попадают в рассчитанные блоки: EFHK 0437, EGLL 3403/4622, EDDF 0122, LSZH 3016, KMSP 3631, KPHL 2747/1772, WSSS 2214, VHHH 5132, VTBS 0747, RKSI 7135.

**Решения пользователя (2026-10-09):**
1. Станция DCL — `X` + индекс аэропорта вылета (EDDF → XDDF), как у TopSky (станция DCL — индекс аэропорта). Опрашивается на земле до взлёта, пока обмен не закончен.
2. Европа, Азия и прочие регионы — ARINC 623 DCL пакетами `cpdlc` (на проводе — как у станций Hoppie: значения в `@…@`). США — PDC telex с той же станции, раскладка как у Delta: `PDC <рейс> <IATA> <IATA>` / `**** PREDEPARTURE  CLEARANCE ****` / `<позывной> DEPARTING <ICAO>  TRANSPONDER <код>` / `SKED DEP TIME <hhmm>   EQUIP  <тип>` / `FILED FLT LEVEL <эшелон>` / `-CLEARED AS FILED-` / маршрут / `CLEARED <SID> DEPARTURE <фикс> TRSN` / `CLB VIA SID` / `EXP <эшелон> 10 MIN AFT DP,DPFRQ <частота>` / `XPCT RWY <ВПП>`. Без «EXC MAINT …» (высота SID неизвестна) и без суффикса оборудования. Нет SID — `UNABLE REVERT TO VOICE`.
3. Сквок: EUR — CAL (строки назначения, гражданские, ENR; орган = префикс страны, аэропорт или FIR вылета; направление; protection и via по назначению и FIR маршрута; пул CCAMS). США — NBCAP (ARTCC = FIR аэропорта по VATSpy, внутренний рейс — назначение в том же ARTCC, сначала первичные блоки). APAC — блоки FIR (I/D), страна по VATSpy `[Countries]`, сноски-ограничения 11–16 не используются, Австралия и Новая Зеландия внутри страны — любой код, кроме международных блоков. Вне таблиц — случайный код. Коды на 00 и специальные коды (банлист) не выдаются никогда.
4. Код 1000 (Mode S) пока не назначается — только в банлисте. Правило Mode S (реальный DCL EDDF выдаёт `SQUAWK 1000`) — отдельная задача `[ПРИ РЕЛИЗЕ]`.
5. Таблицы лежат в репозитории как TS-данные со ссылкой на источник, редакцию и дату. NBCAP — public domain. Условия повторного использования CAL (EUROCONTROL) и eANP (© ICAO) — `[ПРИ РЕЛИЗЕ]` (`08`, решение 9).

**Допущения (одобрены пользователем 2026-10-09):**
1. FSM «RCD RECEIVED» уходит сразу, CLD (и PDC в США) — через 60–180 с, детерминированно от seed. В AIP Сингапура и Малайзии сказано «в течение 5 минут».
2. Запрос принимается в любое время на земле до взлёта (в AIP Сингапура и Малайзии — не раньше чем за 20 мин до TOBT).
3. Если пилот не ответил WILCO за 5 мин, ничего не шлём: текста отмены в источниках нет.
4. Номер PDC — от seed, 001–999. Строки ADT/STARTUP не пишутся: данных нет. Начальной высоты нет: её нет в OFP.
5. NEXT FREQ (DCL) — живой DEL, затем GND VATSIM; иначе OurAirports `DEL`/`CLD`/`GND`; иначе строки нет. DPFRQ (США) — живой APP VATSIM, иначе OurAirports `DEP`/`APP`. OurAirports — данные сообщества (public domain), точность не гарантирована (у EDDF реальный DCL даёт 121.905, в OurAirports такой частоты нет).
6. Названия FIR таблицы APAC сопоставлены с FIR аэропортов по VATSpy.dat `[Airports]` (Китай: ZBPE и т. д.; Япония: ACC-области RJTG/RJBG/RJDG; Австралия: секторы VATSpy «Brisbane (…)» / «Melbourne (…)»).

**Реализация.** Ядро: `packages/core/src/atc/dcl.ts` (запрос, FSM/CLD/CDA, PDC США, отказы), `packages/core/src/atc/squawk/` (`squawk.ts` — выбор кода и банлист, `eur-cal.ts`, `faa-nbcap.ts`, `icao-apac.ts` — сгенерированные таблицы). Станция DCL работает внутри станции ROPS (настройка «Станция УВД ROPS»). Данные: страна и FIR вылета и назначения из VATSpy, частоты аэропорта вылета из OurAirports (`packages/data-sources/src/ourairports.ts`). В духе решения T23 «не конфликтовать с живыми диспетчерами»: если на VATSIM онлайн DEL/GND/TWR аэропорта вылета и включена настройка «Уступать», запрос отклоняется (FSM `RCD REJECTED / REVERT TO VOICE PROCEDURES`).

#### T25 — ROPS: запросы эшелона, скорости, Direct To, логика эшелонов
Ответы на запросы пилота: эшелон, скорость, Direct To — фразеологией CPDLC (CLIMB TO, UNABLE, DUE TO …). Логика эшелона: полукруговое правило и таблица крейсерских эшелонов (ICAO Annex 2, App. 3), RVSM FL290–410, исключения по государствам (AIP; метрические эшелоны — `[ПРИ РЕЛИЗЕ]`), MORA/MEA сектора (из навлога SimBrief: поле `mora` есть, сверено ниже), потолок самолёта из OFP. Direct To — только на точку маршрута впереди. Отказ «из-за трафика» — допущение, только с одобрением.
**Готово, когда:** таблица эшелонов и исключений под тестами; нечётный эшелон в «чётной» зоне отклоняется с правильной причиной.

**Анализ (2026-10-09).**
- Запросы пилота (FBW A32NX `CpdlcMessageElements.ts`, GPL-3.0, только формат; в сети значения без `@`): DM6 `REQUEST <уровень>`, DM9 `REQUEST CLIMB TO <уровень>`, DM10 `REQUEST DESCEND TO <уровень>`, DM18 `REQUEST <скорость>`, DM22 `REQUEST DIRECT TO <точка>`. Уровень — `FL350`, `11000FT` или `8900M`; скорость — `M.78` (FANS-A: M.61–M.92) или `280` / `280KT` (70–350 kt). Ответы FANS-A: UM0 `UNABLE`, UM20 `CLIMB TO <уровень>`, UM23 `DESCEND TO <уровень>`, UM74 `PROCEED DIRECT TO <точка>`, UM106 `MAINTAIN <скорость>` (все WU, кроме UNABLE), UM169 — свободный текст (причины `DUE TO …`). В наборе FANS-A у FBW нет UM166/UM167 (`DUE TO TRAFFIC`, `DUE TO AIRSPACE RESTRICTION` — ATN B1, Doc 4444 Annex 5), их текст идёт как UM169.
- Таблица эшелонов: SERA, Appendix 3 (Рег. (ЕС) 923/2012; совпадает с ICAO Annex 2, App. 3, таблица a, футы, RVSM): 000–179° — FL10, 30 … 290, 310 … 410, 450, 490; 180–359° — FL20, 40 … 280, 300 … 400, 430, 470, 510. Путевой угол — магнитный.
- Исключения, сверенные с AIP: Испания (AIP ENR 1.7-3, AMDT 403/26 от 19-FEB-26) и Португалия (ENR 1.7.5, действует с 01 OCT 2026) — 090–269° нечётные, 270–089° чётные, та же сетка уровней. Франция — так же, но только для IFR в UTA (AIC A 06/20, с 21 мая 2020; таблица — AIP France ENR 1.3.5; нижняя граница UTA и текст ENR 1.3.5 — `[ПРИ РЕЛИЗЕ]`). Новая Зеландия (CAA NZ Part 91, ам. 12) — 270–089° нечётные, 090–269° чётные (зеркально Испании). Италия — то же, что Испания, по документу ENAV о Free Route выше FL335; текст ENR 1.7 Италии не получен — `[ПРИ РЕЛИЗЕ]`.
- Метрические эшелоны (Китай, КНДР; Монголия и страны СНГ — по разным годам переходили на футы): официальные таблицы AIP не получены, есть только вторичные источники и рабочий документ ICAO A36-WP/176 (китайско-российская таблица RVSM в метрах) — `[ПРИ РЕЛИЗЕ]`.
- SimBrief: в каждой точке навлога есть `mora` (ft), `fir`, `fir_units`, `fir_valid_levels` (допустимые эшелоны плеча с учётом направления и ограничений трассы: на M750 в RJJJ — от FL270), `fir_crossing`, `track_mag`. В `general` — `stepclimb_string` (`RCTP/0390` = точка/эшелон в сотнях футов; формат нескольких ступеней на реальном OFP со step climb — `[ПРИ РЕЛИЗЕ]`). Потолка самолёта в OFP нет (в `aircraft` только тип, двигатели, оборудование). Признак RVSM — буква `W` в `aircraft.equip` (поле 10a FPL, Doc 4444, App. 2).
- Телеметрия даёт IAS, но не Mach и не магнитный курс: магнитный путевой угол берётся из `track_mag` текущего плеча навлога.
- Потолок и VMO/MMO — EASA TCDS (сверено 2026-10-09): A.064 A318–A321 iss. 62 (39 800 ft с мод. 30748, VMO 350 kt / MMO 0,82), A.004 A330 iss. 69 (41 450 ft), A.151 A350 iss. 33 (-900 43 100 ft, -1000 41 450 ft), IM.A.120 B737 iss. 29 (NG и MAX 41 000 ft), IM.A.003 B777 iss. 20.0 (43 100 ft), IM.A.115 B787 iss. 30 (-8/-9 43 100 ft, -10 41 100 ft, VMO 350 / MMO 0,90), IM.A.196 B747 iss. 19 (-400 45 100 ft, -8 43 100 ft, VMO 365 / MMO 0,90). A.110 A380 iss. 17 — «см. AFM», чисел нет.

**Решения пользователя (2026-10-09):**
1. Допустимые эшелоны: чётность — своя таблица (SERA App. 3 и исключения ES/PT/FR-UTA/NZ, остальные FIR — по ICAO); ограничения трассы — `fir_valid_levels` SimBrief, когда самолёт на плече навлога (если пересечение со своей таблицей пустое — только своя таблица).
2. Метрические районы (Китай, КНДР) — футовая таблица ICAO (допущение: в Китае реальные эшелоны метрические).
3. Отказ «из-за трафика» (`UNABLE@_@DUE TO TRAFFIC`) — 10 % допустимых запросов эшелона, от seed, не два раза подряд; повтор того же запроса через 5+ мин одобряется.

**Допущения (одобрены пользователем 2026-10-09):**
1. Потолок и VMO/MMO — из TCDS (список выше; у A318–A321 — 39 800 ft, самая распространённая модификация 30748). Тип без данных — без проверки. Потолок по массе не моделируется. Ниже FL100 скорость > 250 kt отклоняется везде (14 CFR 91.117; в SERA — не во всех классах).
2. Direct To — только на точку маршрута впереди, в текущем FIR, не дальше первой точки STAR; иначе `UNABLE`.
3. Ответ — через 20–60 с от seed. Самолёт без `W` в оборудовании — `UNABLE` на FL290–410.
4. Ниже MORA текущего плеча — `UNABLE` без причины.
5. Италия — по ICAO, пока текст AIP Италии ENR 1.7 не получен (`[ПРИ РЕЛИЗЕ]`). Франция — исключение выше FL195 (нижняя граница UTA `[ПРИ РЕЛИЗЕ]`). Новая Зеландия — только FIR NZZC.

**Реализация.** Ядро: `packages/core/src/atc/requests.ts` (разбор запросов и решение), `levels.ts` (таблица и правила государств), `performance.ts` (TCDS), `route.ts` (плечо маршрута, точка входа в STAR). OFP: `OfpFix.trackMag/moraFt/fir/validLevelsFt`, `OfpAircraft.equip`. Станция ROPS отвечает только станции, на которую самолёт залогинен (иначе, как раньше, `MESSAGE NOT SUPPORTED`); решение принимается при получении, ответ — через 20–60 с (очередь в `RopsState.req`, переживает сохранение состояния). Событие `ATC_REQUEST` — в ленте приложения и отчёте replay. Если телеметрии нет — `UNABLE`. Магнитный путевой угол — из `track_mag` плеча, на котором самолёт; плечо без `track_mag` — без проверки чётности.

#### T26 — ROPS: случайные Direct To, step climb, начальная высота снижения
До 3 случайных Direct To за полёт (seeded Rng, только точки впереди по маршруту; ограничения — одобренные допущения ниже). Автоматическое разрешение step climb по ступеням OFP (событие `ALT_CHANGE`, поле ступеней — `general.stepclimb_string`, ниже). Разрешение на снижение с логичной начальной высотой вместо общего «descend via STAR»: по маршруту, фазе, MORA, эшелону перехода назначения. Алгоритм выбора высоты согласовывается как допущение.
**Проверка человеком:** сообщения приходят вовремя в Fenix/FBW/PMDG, принимаются CPDLC-страницей.

**Анализ (2026-10-09).** Оригинал (`01`): клиренс на снижение — за ≤ 20 NM до TOD, step climb — при пересечении 23500/28500 ft, оба через сервер автора. У нас — станция ROPS ядра (T23), фразы FANS-A из T25 (`PROCEED DIRECT TO`, `CLIMB TO`, `DESCEND TO`; FBW также знает `WHEN ABLE PROCEED DIRECT TO`, `AT PILOTS DISCRETION`). Ступени — `general.stepclimb_string` и смены `altitude_feet` в навлоге на этапе `CRZ`. Для начальной высоты снижения есть `mora` по точкам, `transLevelFt` назначения, высоты навлога на этапе `DSC` (профиль SimBrief, не ограничения STAR). Реальных ограничений на случайные Direct To в источниках нет: выбор точек — допущение.

**Допущения (одобрены пользователем 2026-10-09):**
1. Случайные Direct To: 0–3 за полёт от seed; только в крейсере и не ближе 50 NM до TOD; точка в текущем FIR, на 50–250 NM впереди, не SID/STAR, спрямление ≥ 2 NM; `PROCEED DIRECT TO @X@` (WU). *Заменено решением пользователя 2026-10-10 (T38, «Попутно», п. 4): точка выхода из FIR при первом контакте, 50 % на FIR, ≥ 5 NM; до реализации действует это допущение.*
2. Step climb: за 2 мин до точки ступени — `CLIMB TO @FLxxx@` (WU); не шлём, если пилот уже запросил этот эшелон или эшелон не подходит по таблице T25.
3. Снижение: за 20 NM до TOD (как у оригинала). Начальная высота — наибольшая из: высота навлога SimBrief у первой точки STAR; MORA оставшегося маршрута + 1000 ft; округление вверх до 1000 ft. Выше эшелона перехода назначения — `DESCEND TO @FL120@`, ниже — `DESCEND TO @6000FT@`.

**Реализация.** Ядро: `packages/core/src/atc/auto.ts` (точки случайных Direct To, выбор точки, ступени, высота снижения), вызов — `RopsStation.autoClearances` (только залогиненному самолёту с телеметрией, фазы CRUISE/DESCENT; состояние — `RopsState.auto`). OFP: `Ofp.stepClimbs` из `general.stepclimb_string` (`FIX/0410`, первая пара — аэропорт вылета). Точки Direct To — 0–3 случайных расстояния по маршруту в [TOC, TOD − 50 NM], при их прохождении выбирается точка по правилам; если подходящей нет, Direct To не будет. Точки, пройденные больше чем на 30 NM (старт посреди полёта), отбрасываются. Ступень, пройденная больше чем на 20 NM, отбрасывается. Снижение не шлётся, если уже разрешён более низкий уровень или вычисленный уровень не ниже текущей высоты на 1000 ft. Если у назначения нет ни эшелона, ни высоты перехода, граница FL/футы — см. решение ниже. Событие `ATC_AUTO` — в ленте и отчёте replay.

**Решение пользователя (2026-10-09):** случайные Direct To включаются и выключаются: опция ядра `rops.randomDirects` (по умолчанию включена, пишется в заголовок записи полёта), в приложении — настройка «Случайные Direct To». Step climb и снижение от неё не зависят.

**Решение пользователя (2026-10-09, вариант «б»):** если в OFP у назначения нет ни эшелона, ни высоты перехода, граница FL/футы — 18 000 ft только в США и Канаде (ICAO назначения `K…`, `PA…`, `PH…`, `C…`), в остальных регионах всегда эшелон (`FL080`). Канадский район стандартного давления (эшелоны на всех высотах) и прочие территории США (`PG…` и др.) не выделяются — `[ПРИ РЕЛИЗЕ]`. Код — `defaultTransitionFt` в `packages/core/src/atc/auto.ts`.

#### T27 — ROPS: океанический клиренс
Запрос и выдача океанического клиренса, если маршрут входит в океанический район (NAT, PACOTS и т. п.). Формат — по реальным образцам (Shanwick/Gander/New York, data-link OCL). Трек, точка входа, время, эшелон, Mach — из OFP и актуальных треков. Окно запроса — по правилам района (всё закрыто анализом 2026-10-09, ниже).

**Анализ (2026-10-09).** Подробно — `06`, «Океанический клиренс NAT». По NAT OPS Bulletin 2023_001 rev 6 (25 Feb 2026) клиренс в NAT выдаёт только Shanwick; Gander, Santa Maria, Bodø принимают RCL без клиренса, New York и Reykjavik RCL не требуют. Формат CLX, ошибки и окна — NAT OPS Bulletin 2020_001 rev 01. Запрос в Hoppie — CPDLC-пакет FlyByWire `OCEANIC REQUEST …` станции, на которую самолёт залогинен. Треки — natTrak (из NOTAM). Для PACOTS и других районов процедур клиренса не найдено.

**Решения пользователя (2026-10-09):**
1. Только NAT.
2. Ответ по первому океаническому району после OEP: Shanwick — `RCL RECEIVED`, через 2–10 мин CLX, ROGER пилота = CLA → `CLA RECEIVED CLEARANCE CONFIRMED END OF MESSAGE`, без CLA 10 мин — отмена; Gander, Santa Maria, Bodø — `RCL RECEIVED BY <ANSP>`; Reykjavik и New York — `RCL NOT REQUIRED BY <BIRD|KZWY>` (точного текста нет).
3. Ответы — telex от станции, куда пришёл RCL (реальный CLX — ACARS, в нём `/`).

**Допущения (одобрены пользователем 2026-10-09):**
1. Окно запроса — по нашей оценке времени до OEP (расстояние по маршруту / путевая скорость; без скорости — средняя скорость OFP); время пилота идёт только в `FM <OEP>/<ETO>`.
2. Маршрут CLX — точки-координаты OFP после OEP и следующая именованная точка (выход), как в примере Shanwick. `NAT <буква>`, если точки совпадают с действующим треком natTrak (действие трека — на момент пересечения 30W), иначе `RANDOM ROUTE`. Перемаршрутизаций нет.
3. Эшелон: запрошенный, если он есть у трека (вне трека — по таблице T25 на первом океаническом плече); иначе ближайший допустимый не выше MAX (при равенстве — ниже) и `ATC/ LEVEL CHANGE`; нет такого — `RCL/CLA RECEIVED NEGOTIATION REQUIRED CONTACT SHANWICK BY VOICE`. Мах — запрошенный. Случайных отказов нет.
4. Точка входа не на маршруте впереди, неверный позывной, Мах или эшелон — `RCL REJECTED` с причиной из бюллетеня.

**Реализация.** Ядро: `packages/core/src/atc/oceanic.ts` (`OclService`: разбор RCL, район, окна, CLX, CLA, переклиренс с `ATC/ … RECLEARANCE n`), вызов из `RopsStation` (RCL и ROGER на любую станцию ROPS; состояние — `RopsState.ocl`). Треки — `ExtDataUpdate.natTracks`, адаптер `packages/data-sources/src/nattrak.ts` (источник `nattracks`, только со станцией ROPS, раз в час). Событие `ATC_OCL` — в ленте приложения и отчёте replay. Номер CLX (`CLRNCE nnn`) — от seed, как номер PDC в T24. На маршруте без района NAT RCL получает, как раньше, `MESSAGE NOT SUPPORTED BY THIS ATS UNIT`. Тесты — на синтетическом OFP EGLL–KJFK по реальному треку E; реальный трансатлантический OFP (поля `fir`, `tracks`, тип точек-координат) — `[ПРИ РЕЛИЗЕ]`.

#### T28 — Пуски ракет рядом с маршрутом
Адаптер TheSpaceDevs Launch Library (версия и лимиты — сверены, ниже; кэш обязателен), сценарий в `external/`: пуск в пределах 300 NM от маршрута и в окне времени полёта. Только реальные данные; нет пуска — нет сообщения. Данные пишутся в запись полёта.
**Готово, когда:** фикстура реального ответа, тест расстояния и окна, деградация без сети.

**Анализ (2026-10-09).** Подробно — `06`, «Внешние данные». Текущая версия — Launch Library **2.3.0** (`ll.thespacedevs.com/2.3.0/`), без ключа 15 запросов в час на IP (страница thespacedevs.com/llapi и `/2.3.0/api-throttle/`). Координаты площадки есть только в `mode=normal`. Статусы и точность T-0 — справочники `/2.3.0/config/launch_statuses/` и `/net_precisions/`. Лицензия данных на сайте не указана — `[ПРИ РЕЛИЗЕ]`. Реального формата такого сообщения авиакомпании нет.

**Решение пользователя (2026-10-09):** сообщаются пуски со статусом Go **и уже состоявшиеся** (в полёте, успех, полезная нагрузка выведена, авария, частичная авария).

**Допущения (одобрены пользователем 2026-10-09):**
1. Запрос в начале полёта и раз в час, кэш 30 мин, после ошибки — пауза 15 мин. Окно запроса — от часа до начала полёта до «сейчас + блок-тайм OFP + 1 ч» (оставшееся время сервис не знает; лишнее не мешает). Время — реальное UTC. Без сети — нет сообщения.
2. Go — только с точностью T-0 до часа или точнее; TBD, TBC, Hold не берутся.
3. Одно сообщение за полёт, в крейсере: площадка ≤ 300 NM от маршрута впереди; Go — окно пуска не закрыто и T-0 до ETA, состоявшийся — T-0 после взлёта. Несколько — ближайший по маршруту.
4. Текст — свой шаблон (`SPACE LAUNCH NEAR ROUTE` / ракета / миссия / площадка / `NET hhmmZ WINDOW hhmm-hhmmZ` или `LAUNCHED hhmmZ <статус>` / расстояния / `EXPECT AIRSPACE RESTRICTIONS CHECK NOTAM`, подпись `SOURCE THESPACEDEVS`).

**Реализация.** Адаптер — `packages/data-sources/src/launches.ts`, источник `launches` в `ExternalDataService`. Ядро: `SpaceLaunch` и `ExtDataUpdate.launches` (`core/src/ext/data.ts`, площадки дальше 300 NM отбрасываются при получении, данные в записи полёта), переменные `ext.launch_*` (`scenario/context.ts`, `05`). Сценарии — `packages/scenarios/external/space_launch.yaml` (Go) и `space_launch_done.yaml`, взаимоисключаются.

#### T29 — Special Events (результаты спортивных матчей и т. п.)

#### T30 — CONNEX schedule: стыковочные рейсы авиакомпании
**Переоткрыта 2026-10-15 (решение пользователя):** AeroDataBox, ключ вводит пользователь. Отмена 2026-10-09 (вариант «г») исходила из «ключ в клиенте запрещён», но инвариант 2 допускает ключ, введённый пользователем и хранимый в хранилище ОС (`apps/desktop/src/main/secrets.ts`).

Постановка: перед прилётом — список реальных стыковочных рейсов той же авиакомпании из пункта назначения: рейс, направление, время, гейт. Источник у оригинала — AeroDataBox (RapidAPI, `01`). Реальный рейс заменяет синтетический в `short_connection`/`connection_*` (T42 п. 12).

**Источник (сверено 2026-10-15).** AeroDataBox, спецификация OpenAPI v1.15.4.0 (`doc.aerodatabox.com/docs/openapi-rapidapi-v1.json`): FIDS `GET /flights/airports/icao/{ICAO}/{fromLocal}/{toLocal}` — Tier 2, 2 единицы; RapidAPI — `https://aerodatabox.p.rapidapi.com/`, заголовки `X-RapidAPI-Key`, `X-RapidAPI-Host: aerodatabox.p.rapidapi.com`. Тарифы (`aerodatabox.com/pricing`): Basic на RapidAPI — бесплатно бессрочно, 400 единиц/мес (≈200 запросов FIDS), 1 запрос/с, окно FIDS ≤ 12 ч, расписание до 365 дней вперёд; сверх квоты запросы отклоняются (без доплат). Поля рейса: `number`, `airline.icao`, `codeshareStatus` (`IsOperator`/`IsCodeshared`/`Unknown`), `status`, `isCargo`, `movement.airport.icao`, `movement.scheduledTime.utc`, `movement.terminal`, `movement.gate`, `movement.quality`. Условия (`aerodatabox.com/terms`, ред. 2026-10-11): п. 5.3 — коммерческое использование только с платного канала; п. 5.4 — при бесплатном канале обязательна атрибуция AeroDataBox; п. 5.5 — хранение данных не дольше 7 дней (п. 5.8: идентификаторы — номер рейса, код аэропорта — бессрочно); пп. 6.1.2, 6.1.5 — ключ не передаётся третьим лицам; п. 5.2(a) — запрет реальной навигации и лётной эксплуатации (симулятор не затрагивает); п. 2.4 — условия маркетплейса регулируют только оплату.

**Допущения (одобрены пользователем 2026-10-15, без изменений):**
- **C1. Ключ пользователя.** Пользователь сам подписывается на RapidAPI и вводит свой ключ; ключ хранится в `SecretStore` (`safeStorage`) и уходит только в заголовке к `aerodatabox.p.rapidapi.com`. Мы ключ не получаем и данные не перепродаём: клиент AeroDataBox — пользователь, приложение — его программа. В условиях такой сценарий прямо не описан; толкование — разрешён (ключ никому не передаётся, данные видит только владелец).
- **C2. Передача через Hoppie.** Сообщение со стыковкой (номер рейса, направление, STD, гейт) идёт через сервер Hoppie в самолёт самого пользователя — считается использованием данных самим пользователем, а не распространением третьим лицам.
- **C3. Некоммерческое использование.** В настройках — пояснение: ключ на бесплатном тарифе — только для личного некоммерческого использования (п. 5.3).
- **C4. Атрибуция.** Последняя строка тела каждого сообщения с этими данными — `SRC AERODATABOX`; в настройках рядом с полем ключа — ссылка на aerodatabox.com.
- **C5. Один запрос за рейс** при старте рейса (как только известен OFP). Окно — местное время аэропорта назначения от STA+30 мин до STA+4 ч; `direction=Departure`, `withCargo=false`, `withPrivate=false`, `withCancelled=false`, `withLeg=false`. Местное время — по `ofp.destination.utcOffsetH`, дата — из OFP (не текущая). Повтор — один, после паузы, при 5xx или таймауте; при 429 и 401 — до конца рейса без запросов. Обновления гейта перед TOD нет.
- **C6. Выбор рейсов.** Кандидаты — вылеты той же авиакомпании (`airline.icao == ofp.airlineIcao`); если рейс есть и как операторский, и как код-шеринговый, — операторский (`IsOperator`). Как реально заполняются `airline` и `codeshareStatus` у код-шеринговых рейсов — **[ПРОВЕРИТЬ]** на живом ответе (проверка человеком). Рейс для `irr.connect_flight` — по seed среди кандидатов первых 2 ч после STA+30; если там пусто — среди всего окна.
- **C7. Число пассажиров синтетическое:** `irr.connect_pax` — по-прежнему от `ops.transfer_pax` (реальной загрузки нет ни в одном API).
- **C8. Переменные и сценарий.** `irr.connect_dest` (куда летит стыковочный рейс), `irr.connect_gate` (гейт или терминал, если известен). Новый сценарий `connex_list`: за 120 NM до TOD — до 4 вылетов авиакомпании с направлением, STD и гейтом. `short_connection` и `connection_*` используют реальный рейс.
- **C9. Детерминизм и хранение.** Нужные поля ответа идут во вход ядра `CoreInput.data` и в запись полёта (реплей детерминирован). При запуске приложения в записях старше 7 дней эти данные вычищаются, номера рейсов и коды аэропортов остаются (п. 5.8); реплей такой записи идёт по фолбэку, `--check` предупреждает. Кэша на диске нет — только в памяти на рейс.
- **C10. Фолбэк.** Без ключа, при ошибке, ответе 204, без кандидатов, без `airlineIcao` или `utcOffsetH` — как раньше: `ONWARD FLT` по OpenFlights или ничего. Тестовый флаг `syntheticConnections` остаётся.
- **C11. Только RapidAPI.** API.Market (бесплатный тариф там пробный) и прямой доступ (от $19/мес) — `[ПРИ РЕЛИЗЕ]`; базовый адрес и заголовок ключа меняются в одном месте адаптера.

### Приоритет 2

#### T31 — Имитация линии передачи: VHF, спутники, SATCOM, задержка
Ядро выбирает наземную VHF-станцию в прямой видимости или (при SATCOM в профиле самолёта) спутник и задаёт задержку доставки. База VHF-станций — из проверяемых источников (`[ПРОВЕРИТЬ]`: открытого авторитетного списка SITA/ARINC может не быть — тогда только с одобрением). Спутники: Inmarsat (GEO), Iridium (TLE CelesTrak + SGP4, лицензия библиотеки `[ПРОВЕРИТЬ]`). Задержки — по реальным данным. TLE и база — в записи полёта.

**Допущения (одобрены пользователем 2026-10-15, без изменений; по `docs/_drafts/T31-T32-research.md`, A1–A11):**
- A1–A2: VHF-«станция» — ближайший аэропорт из OurAirports в пределах радиогоризонта (`1.23·√h_ft` НМ, потолок ~200 НМ); помечается «условная станция». Формулу сверить с источником до реализации.
- A3: спутник Inmarsat GEO — по долготе и углу места (> 5°); позиции 54°W, 15.5°W, 64.5°E, 178°E, 98°W, 25°E, 143.5°E.
- A4, A6, A10: Iridium, TLE и SGP4 **вынесены из T31** в отдельную карточку (условия CelesTrak/Space-Track и протокол ACARS через Iridium не выяснены). Когда дойдёт: SGP4 (`satellite.js`, MIT) вне ядра, позиции — в `CoreInput.data`; TLE не коммитить и не распространять.
- A5: задержки VHF 2–10 с, Inmarsat 5–30 с — конфигурируемые константы без источника, детерминированный jitter из `Rng`.
- A8: GES-код — по таблице L-band из исследования; для неоднозначного `02` — первый по таблице.

**Сделано (2026-10-15).** `packages/core/src/datalink/link.ts` (чистый TS): `chooseLink` — VHF (ближайший аэропорт из коридора маршрута в пределах `min(200, 1.23·√h_ft)` NM; на земле 20 NM), иначе при `datalink.satcom` спутник Inmarsat с наибольшим углом места ≥ 5° (7 позиций A3), иначе линии нет; `LinkChannel` — очередь: сообщение ждёт линию, затем задержку VHF 2–10 с / SATCOM 5–30 с (A5, константы `DELAY_MS`, детерминированный jitter из `Rng` `<seed>/#link`, FIFO), выходит с меткой `link` (`kind`, `station`, `delayMs`, `waitedMs`); без телеметрии сообщения проходят как раньше. `CoreOptions.datalink`, `CoreState.link` (сохраняется), `AcarsCore.linkView` (линия сейчас, сколько ждёт/в пути — для окна T32). Станции — `ExtDataUpdate.vhf` (в записи полёта, `ExtState.vhf`); адаптер `fetchVhfStations` (OurAirports `airports.csv`), источник `vhf` в `ExternalDataService` (`startFlight(…, { datalink: true })`). Приложение: настройки «Имитация линии передачи» и «На самолёте есть SATCOM» (по умолчанию выключено / включено), `header.datalink` в записи, replay.
**Уточнение A2 (одобрено пользователем 2026-10-15):** формула `1.23·√h` даёт 0 на земле, поэтому на земле радиус VHF — постоянные 20 NM (иначе у гейта нет линии). Станции — только крупные и средние аэропорты с регулярными рейсами, в коридоре 300 NM от плановой трассы; вне коридора (например, диверсия далеко в сторону) остаётся SATCOM или ожидание. Формула радиогоризонта `1.23·√h` — общеизвестное приближение, первоисточник для цитирования не искал.
**Проверка человеком:** включить «Имитацию линии» в настройках, лететь рейс с живыми данными: сообщения приходят на 2–30 с позже, чем с выключенной настройкой; над океаном без SATCOM сообщения не приходят, пока не появится станция.
**Не вошло (по A4/A6/A10):** Iridium, TLE и SGP4 — отдельная будущая карточка.


#### T32 — Заголовки AES/GES и окно состояния линии
Динамический заголовок по реальным образцам (`AES:… GES:… .<рег>`), ICAO hex борта (ввод в профиле или источник `[ПРОВЕРИТЬ]`), правило переноса для узких дисплеев. Окно в приложении: станция или спутник, время передачи. Зависит от T31.

**Допущения (одобрены пользователем 2026-10-15, без изменений):**
- A7: заголовок AES/GES — формат декодеров, не кабинный; показывается в окне состояния, в тексте сообщения — по опции, выключено по умолчанию.
- A9: ICAO hex — ввод в профиле самолёта; без него заголовок не выводится. Открытые базы (OpenSky, ADS-B Exchange) не используем до `[ПРИ РЕЛИЗЕ]`.
- A11: перенос заголовка по токенам (`AES:…` / `GES:… 2` / `.REG`), токен длиннее строки — жёсткий перенос форматтера; заголовок проходит форматтер (инвариант 9).

**Сделано (2026-10-15).** Ядро: `aesHeaderTokens` (`AES:<hex> GES:<код> 2 .<рег>` — формат образцов декодеров), `gesCode` (таблица A8: AOR-W 43, AMER 05, APAC 50, EMEA 90; для AOR-E, IOR, POR кода нет — заголовка нет, кода не выдумываем), `linkHeaderLines` / `withLinkHeader` в `format/formatter.ts` (перенос по токенам, жёсткий перенос длинного токена, повторная разбивка на страницы; сообщения по-прежнему создаёт только форматтер). `OutboundMessage.link.header`; `AcarsCore.linkView` теперь отдаёт `header` и `last` (когда ушло последнее сообщение и сколько держала линия). `CoreOptions.datalink`: `icaoHex`, `headerInText` (по умолчанию выключено; заголовок только на SATCOM, не на VHF и не у CPDLC). Приложение: настройки «ICAO-адрес самолёта» (6 hex, пусто = нет заголовка; открытые базы не используются) и «Вставлять заголовок в текст сообщения»; строка «Линия передачи» в панели статуса (VHF станция и расстояние / SATCOM спутник и угол места / нет линии, заголовок, сколько ждёт и в пути, время и задержка последнего сообщения); `header.datalink` записи хранит `icaoHex` и `headerInText`.
**Проверка человеком:** в настройках ввести ICAO-адрес своего борта и включить линию; над океаном/Тихим океаном в панели статуса видна строка SATCOM со спутником и заголовком `AES:… GES:… 2 .РЕГ`; с опцией «в текст» первые строки сообщения на CDU — заголовок, перенесённый по токенам на узком дисплее.
**Уточнения T31/T32 (одобрены пользователем 2026-10-15):** на земле радиус VHF 20 NM; станции — крупные и средние аэропорты с регулярными рейсами в коридоре 300 NM; первый GES-код спутника из таблицы, для AOR-E/IOR/POR заголовка нет; один ICAO-адрес на все борта; формула `1.23·√h` без сверки с первоисточником.
**Известные ограничения:** ICAO-адрес один на все борта (не по регистрации); у спутников AOR-E, IOR, POR заголовка нет, пока не найден источник GES-кодов.


#### T33 — Пожар у аэропорта назначения
Нестандартный сценарий: пожар рядом с ВПП, влияние на видимость, рекомендация подготовить диверсию, продолжение через ~20 мин. Условия (ВПП из OFP/METAR, ветер) — реальные.
**Сделано (2026-10-15).** `irregular/dest_fire.yaml`: за 120 NM до назначения, вероятность 0,02, только если известны плановая ВПП и ветер METAR назначения. Телекс: пожар у ВПП, румб сноса дыма и ветер из METAR, «VIS REDUCED IN SMOKE», подготовить диверсию на запасной; ответ HOLD (по умолчанию, `flight.hold: 20`, выдаёт ROPS) или DIVERT; через 20 мин — «UNDER CONTROL, ARRIVALS RESUMED».
**Допущения (одобрены пользователем 2026-10-15):** 1) число видимости в тексте не называется — «снижена дымом» без метров, фактическая видимость пилоту видна в METAR/симуляторе; 2) сторона ВПП, у которой пожар, не указывается (источника нет); 3) 20 минут и вероятность 0,02 — из карточки и по аналогии с `drone_activity`; 4) «пожар» — случайное событие, а не данные реального инцидента (как и остальные irregular).


#### T34 — Эффекты в симуляторе: столб дыма с учётом ветра
По T33 мост создаёт объект с эффектом дыма у ВПП (SimConnect, пакет для Community). Ветер — из симулятора. Влияние на производительность ограничено. Зависит от T21, T33.
**Проверка человеком:** MSFS 2024, сценарий T33: дым виден издалека, сносится по ветру, FPS не падает заметно.
**Решение пользователя (2026-10-15):** свой SimObject-пакет для Community с FX дыма, спавн через `AICreateSimulatedObject_EX1`, координаты ВПП из OurAirports, ветер и снос — движок эффектов, проверка человеком в MSFS.
**Сделано (2026-10-15).** Шаг сценария `smoke: start|stop` (ядро → команда `smoke` с аэропортом и ВПП, в запись и replay); `dest_fire` включает дым с первым телексом и гасит после «UNDER CONTROL» (при DIVERT дым остаётся). Приложение (`controller.ts`) берёт середину ВПП из OurAirports `runways.csv` (`ExternalDataService.runwayPoint`, кэш 30 дней; нет ВПП или сети — строка в ленте) и шлёт мосту `smoke_start {lat, lon}`; `smoke_stop` — по сценарию, при остановке рейса и выходе. Мост: команды в `CommandCatalog`, `SmokeController` (создать при подлёте ≤ 40 NM, убрать > 60 NM, через 90 мин, по stop; в новой сессии SimConnect создаёт снова), `SimConnectSource.ApplySmoke`. Пакет — черновик `bridge/msfs/package/` (README там).
**Отклонение от решения:** `AICreateSimulatedObject_EX1` нет в локальной обёртке SimConnect (`SimConnectLibs/sdk2024`, проверено 2026-10-15; в `SimConnect.dll` экспортируется только `AICreateSimulatedObject`), а обычный вызов работает лишь с немодульными объектами. Поэтому объект — немодульный контейнер `aircraft.cfg` и вызывается обычная функция; с официальным SDK (T19) вызов заменяется на `_EX1` в одном месте (`ApplySmoke`).
**Допущения (одобрены пользователем 2026-10-15):** 1) дым стоит в середине плановой ВПП (какая сторона горит — неизвестно, как и в T33); 2) объект создаётся при подлёте ≤ 40 NM (дальше сцена не загружена — не проверено), убирается > 60 NM; 3) живёт не более 90 мин; 4) `Altitude = 0`, `OnGround = 1` (SDK не описывает их связь); 5) внешний вид дыма нужно сделать в Visual Effects Editor — `FX_GUID` в `ACARS_Smoke.xml` пока нулевой.
**Проверка человеком (уточнение):** см. `bridge/msfs/package/README.md`, «To finish»: создать эффект, собрать пакет, положить в Community, запустить `dest_fire` ближе 40 NM к аэродрому — дым у ВПП виден издалека, наклонён по ветру, FPS не проседает.

Причина: `Entry` считает параметры `from`/`to`/`phase` любой системной строки фазами полёта и переводит их как `phase.<значение>`, а `atc_handover` (`session.ts`) передаёт в `from`/`to` позывные станций (`XFIN`) → ключа `phase.XFIN` нет. Запись остаётся в ленте, поэтому View → Reload падает снова. Main-процесс и полёт при этом работают.
1. Переводить как фазу только параметры строки `phase` (или переименовать параметры `atc_handover`, например `fromStation`/`toStation`).
2. `translator`: неизвестный ключ не роняет интерфейс (ключ как текст + `console.error`).
3. React error boundary вокруг ленты и вкладок: ошибка одной записи не гасит окно.
4. Main: обработчик `render-process-gone` / `unresponsive` — запись в журнал, перезагрузка окна.
**Готово, когда:** тест рендера ленты на каждый `SystemCode` с параметрами, как их шлёт `session.ts` (в том числе `atc_handover`); тест `translator` на неизвестный ключ.
**Проверка человеком:** полёт через 2 FIR с логоном на ROPS: на передаче строка «ROPS: передача XFIN → X…», окно не пустеет.

**Попутно — второй баг того же полёта.** Все три случайных Direct To (T26) пришли на один и тот же фикс `TEKVA`, пилот каждый раз отвечал WILCO. Причина (по коду): `autoClearances` → `directCandidate` (`atc/auto.ts`, `atc/rops.ts`) не помнит выданные фиксы и не учитывает, что самолёт уже летит прямо на фикс: позиция на маршруте (`routePosition`) — проекция на линию OFP, и пока фикс в 50–250 NM впереди, он снова даёт «спрямление» ≥ 2 NM.

2. Кандидаты следующего Direct To — только фиксы после последнего выданного; фиксы между позицией и выданным фиксом считаются пропущенными.
3. Повторно один и тот же фикс не выдаётся никогда.
4. **Не случайная точка, а логика (просьба пользователя 2026-10-10; одобрено пользователем 2026-10-10: логика, вероятность 50 % на FIR, порог 5 NM — заменяет допущение 1 T26).** Источник по реальной практике — `[ПРОВЕРИТЬ]` до кода (если практика окажется другой — вернуться к пользователю) (ICAO Doc 4444, EUROCONTROL Free Route Airspace, руководства ATC); в T26 записано, что ограничений в источниках не нашли, поэтому всё ниже — допущения.
   - **Куда:** точка выхода из текущего FIR по маршруту OFP (последний фикс маршрута в FIR — диспетчер ведёт борт до своей границы). Если она дальше 250 NM — самый дальний фикс маршрута в FIR в пределах 250 NM. Не SID/STAR, не дальше TOD − 50 NM.

#### T51 — Irregular: случайный момент в крейсере и аэропорт в ответе `DIVERT <ICAO>` **Р**
Найдено при разборе 2026-10-15. (1) Триггер `on: phase, phase: CRUISE` — фронт «в фазе и условия истинны» (`engine.ts`, `triggered`): сценарий стартует на первом тике крейсера, т. е. примерно через минуту после выхода на эшелон (CLIMB → CRUISE, 60 с устойчивости, `04`). `medical_onboard`, `unruly_passenger`, `ped_fire_cabin`, `tech_defect_mel` никогда не случаются в середине или конце крейсера. **Часть А — случайный момент в крейсере. Предложение п. 1–6 одобрено пользователем 2026-10-15 как есть:**
1. Охват: `medical_onboard`, `unruly_passenger`, `ped_fire_cabin`, `tech_defect_mel`. Новости T29 (`special_news`), внешние события, `curfew_dest`, `fuel_monitoring`, `emergency_*` — без изменений (они привязаны к данным или к условию, а не к случайности).
2. Механизм движка: новое поле триггера `window: { after_min: 10, until: "<условие конца>" }` для `on: phase`. На фронте (вход в крейсер, условия истинны) — как сейчас бросок `probability` (seed того же сценария, частота за рейс не меняется); при успехе выбирается доля `f` ∈ [0, 1) (seed) и сценарий **откладывается**, а не стартует.
3. Момент — по **доле оставшегося пути**, а не по часам: при входе запоминается `T0 = flight.minutes_to_tod`; старт, когда `flight.minutes_to_tod ≤ T0 − 10 − f × (T0 − 10 − порог)`, где порог — из условия сценария (30 мин для медицины и дебошира, 20 — для пожара, 30 — для MEL). Так момент не зависит от паузы, ×N и ветра и всегда попадает в окно. Равномерно в окне [выход на эшелон + 10 мин; TOD − порог]. «+10 мин» (табло «пристегнуть ремни» гаснет, начинается сервис) — игровое число.
4. В момент старта заново проверяются условия сценария, `cooldown` и `excludes`: если за это время началась диверсия или сработал взаимоисключающий сценарий — пропуск (`SCENARIO_SKIPPED`, причина как сейчас). Взаимоисключение сохраняется: первым придёт тот, чей момент раньше.
5. Окно короче 10 мин (короткий крейсер) — сценарий не идёт, как и сейчас при `minutes_to_tod` < порога.
6. Отложенный старт — часть состояния движка (сериализуется), запись и replay детерминированы. «Запустить сейчас» работает как раньше (без окна).

**Часть Б — `DIVERT <ICAO>` в ответе. Предложение п. 1–6 одобрено пользователем 2026-10-15 как есть:**
1. Охват — все ветки DIVERT: `medical_onboard`, `cmd_medical`, `unruly_passenger`, `ped_fire_cabin`, `emergency_mayday`, `emergency_pan`, `drone_activity`, `dest_fire`, `runway_closure_dest`.
2. Новая переменная запуска `reply.icao`: первое слово `reply.arg`, если это **известный** аэропорт — из OFP (вылет, запасные, ERA/ETOPS по T50) или из OurAirports `airports.csv` (уже грузится для T29). Проверка по справочнику нужна, потому что 4-буквенные слова (`SICK`, `PAIN`, `CALM`) иначе приняли бы за ICAO. Без загруженного справочника — только аэропорты OFP. Не назначение и только в воздухе — как у команды `DIVERT`. Остаток после ICAO — `reply.arg` для `CREW INFO`.
3. Ветки: `set: { flight.divert: "{reply.icao|or:<как сейчас>}" }` — без ICAO поведение прежнее (ближайший по T50 или запасной OFP); таймаут с `default: DIVERT` (пожар, MAYDAY) — тоже прежний выбор.
4. Пригодность аэропорта, названного пилотом, не проверяется — решение КВС (в реальности так же). Расстояние в ответе — если известны координаты (OFP или `airports.csv`), иначе строка не печатается.
5. Неизвестный ICAO (`DIVERT ZZZZ`) — диверсия на выбор по умолчанию и строка «ZZZZ UNKNOWN, DIVERT <аэропорт>» в ответе. Текст одобрен.
