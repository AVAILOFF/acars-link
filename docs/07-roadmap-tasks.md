## Этап 5 — Функции уровня RealAcars / RealAcars Plus

Решение пользователя 2026-10-09: реализовать функции оригинала (бесплатного RealAcars и анонсов RealAcars Plus), которых у нас нет. Код оригинала не копируется (инвариант 1), только идеи из публичных описаний.

### Правило реализма и проверки данных (для всех карточек этапа 5)

1. **Максимальный реализм.** Формат, фразеология, тайминги и логика — как в реальной эксплуатации. Образцы сообщений берутся из реальных источников (ICAO Doc 4444 и набор сообщений CPDLC, ARINC 620/623, AIP, реальные распечатки ACARS). Источник образца указывается в комментарии к сценарию или таблице.
2. **Максимальная проверка данных.** Коды, частоты, правила эшелонов, диапазоны сквоков, границы FIR, станции, спутники, расписания, поля API — только из проверенного источника. В `06-integrations.md` (или рядом с таблицей) записываются источник, дата сверки и лицензия. Не угадывать: место без источника помечается `[ПРОВЕРИТЬ]` и проверяется до использования.
3. **Допущения — только с одобрением.** Упрощение, приближение, эвристика или синтетические данные разрешены, но **до реализации** их нужно перечислить пользователю: что допускаем, почему нет реальных данных, чем это отличается от реальности, заметит ли пилот. Без явного «да» допущение не реализуется. Одобренные допущения записываются в карточку (подраздел «Допущения») с датой.
4. **Таблицы под тестами.** Каждая таблица правил (запрещённые сквоки, эшелоны, диапазоны) покрыта тестами на реальных примерах. Ответы внешних API — урезанные реальные фикстуры. Внешние данные попадают в запись полёта (replay детерминирован).
5. Инварианты не ослабляются: числа не от LLM (8), всё через форматтер (9), ключи только у пользователя или на бэкенде (2), уважение к сети Hoppie (6).

### Приоритет 1

#### T21 — Канал команд «приложение → мост»
Протокол моста v2: кроме телеметрии, приложение отправляет команды (белый список типов, валидация, подтверждение или ошибка). Слушает только 127.0.0.1. Ядро выдаёт новый тип выхода «команда симулятору», рядом с «отправить сообщение». Это основа для T22 и T34.
**Готово, когда:** fake-источник принимает и подтверждает команды, тесты протокола в `bridge:test` и в `apps/desktop/test` зелёные, v1-клиенты не ломаются.

#### T22 — Свои сообщения на VDGS через GSX
Вывод текста от авиакомпании на табло VDGS (гейт, номер рейса, приветствие, сообщения сценариев: новый шаг `vdgs:`). `[ПРОВЕРИТЬ]` по документации FSDreamTeam: механизм (L-переменные, файл или API GSX Pro), длина и набор символов, версия GSX. Без GSX функция молча выключена. Зависит от T21.
**Проверка человеком:** MSFS 2024 + GSX Pro, аэропорт с VDGS от GSX, прилёт на стоянку: текст появляется на табло, не мешает парковке.

**Анализ (2026-10-09).** Источник — руководство FSDreamTeam «VGDS Custom Messages System» от 2025-07-29, оно поставляется с GSX Pro (`couatl\GSX\SDK\Samples\VGDS\vgds_developer_manual.pdf`), подробно в `06`, «GSX VDGS». Механизм — JSON-файлы в `%APPDATA%\Virtuali\GSX\VGDS\`, GSX перечитывает их сам. L-переменных и API нет, мост не нужен. Лимиты: small 4×2 (на стоянке), narrow 6×6, wide 9×7, x 10×7. Набор символов в источнике не описан. Когда GSX показывает сообщение и не перебивает ли оно указания по парковке — тоже не описано, это проверка человеком.

**Решение пользователя (2026-10-09):** файл пишет main-процесс приложения (`apps/desktop/src/main/vdgs.ts`), не мост. От T21 используется только тип выхода ядра `CoreOutput.commands` (команда `vdgs`).

**Допущения (одобрены пользователем 2026-10-09):**
1. Сообщение фильтруется только по аэропорту прилёта (или диверсии), без фильтра по гейту: имена гейтов OFP/OSM/`ops.arr_gate` могут не совпасть с `gate_name`/`gate_number` GSX.
2. `valid_from`/`valid_until` не используются (время симулятора может отличаться от реального). Приложение владеет одним файлом `acars-sim.json`, пишет его атомарно и удаляет в конце рейса, при выходе и при запуске приложения.
3. GSX считается установленным, если есть папка `%APPDATA%\Virtuali\GSX`. Нет папки — функция молча выключена.
4. Шаг `vdgs:`: `narrow` обязателен, `wide` и `x` без своих строк берут `narrow`, `small` выводится, только если задан. Строка, которая не помещается, — ошибка (литерал — при загрузке сценария, шаблон — `SCENARIO_ERROR` при выполнении), без сокращений.
5. Символы: только A–Z, 0–9, пробел и `- / . :`. Значения (рейс, гейт, аэропорт) подставляет ядро. Переменные SimBrief самого GSX не используются (инвариант 8).

#### T23 — ROPS: станция, CPDLC-логон, учёт FIR
Имитация станции УВД через Hoppie: логон пилота на станцию, ответ с текущим органом УВД. При пересечении границы FIR сообщение о логоне обновляется (передача связи, как CDA/NDA в реальном CPDLC). Границы FIR — внешние данные во входе ядра, проверка «точка в полигоне» в ядре.
**Открытые вопросы (до кода):** позывной станции на общей сети Hoppie (уникальный на пользователя? правила Hoppie `[ПРОВЕРИТЬ]`, согласование с Hoppie из `02`); тип пакета `cpdlc` или `telex`; какие самолёты поддерживают CPDLC через Hoppie; поведение, когда на VATSIM онлайн живой диспетчер этого сектора (не конфликтовать). Источник границ FIR (VATSpy data project или другой) — лицензия `[ПРОВЕРИТЬ]`.
**Проверка человеком:** FBW A32NX и PMDG 777, логон на станцию, полёт через 2+ FIR: сообщения приходят на границах.

**Анализ (2026-10-09).** Подробно — `06`, «CPDLC через Hoppie» и «Границы FIR». Правил о позывных станций у Hoppie нет. Живые станции VATSIM заходят под 4-буквенными кодами (EDGG, EDYJ, LONC). Логон и передача связи у Hoppie — только пакеты `cpdlc` (`/data2/<min>/<mrn>/<ra>/<text>`), telex самолёты так не обрабатывают. Фразы взяты из кода FBW A32NX и перехваченных пакетов сети: `REQUEST LOGON` → `LOGON ACCEPTED`, `CURRENT ATC UNIT@_@<код>@_@<имя> CTL`, `HANDOVER @<код>`, `LOGOFF`. Границы FIR — VATSpy Data Project (CC BY-SA 4.0). Какие самолёты поддерживают CPDLC через Hoppie: FBW A32NX (по коду). iniBuilds A350/A380 шлют `REQUEST LOGON` (проверено в T09). Остальные — проверка человеком.

**Решения пользователя (2026-10-09):**
1. Позывной станции — `X` + три последние буквы FIR (EDGG → XDGG). Индексов ИКАО на X нет: станция не перехватывает логоны чужих пилотов и не мешает живым диспетчерам. На границе FIR — настоящая передача связи (`HANDOVER @XDWW`), самолёт сам логинится на следующую станцию.
2. Пакеты УВД — `cpdlc`, сообщения авиакомпании остаются `telex`. Для текста CPDLC в форматтере свой профиль: без `/` (FBW читает текст как шестое поле через `/`), `@` и `_` разрешены.
3. Если на VATSIM онлайн центр (CTR/FSS), покрывающий FIR, станция уступает: подключённому самолёту — уведомление `VATSIM ATC ONLINE@_@CONTACT <позывной> @<частота>@` и `LOGOFF`, на логон — `UNABLE` с тем же текстом. В следующей FIR или после ухода диспетчера станция снова принимает логон. Настройка «Уступать живым диспетчерам VATSIM», по умолчанию включена.

**Допущения (одобрены пользователем 2026-10-09):**
1. Границы FIR — из VATSpy `Boundaries.geojson` (данные VATSIM, приближение реальных FIR). Файл скачивается приложением и кэшируется на 7 дней, в репозитории только урезанная фикстура для тестов.
2. Только FIR (4-буквенные области VATSpy), без UIR и секторов. Где области перекрываются, первыми идут области, которые служат FIR какого-нибудь аэропорта (`[Airports]` VATSpy.dat): накладные области без аэропортов (`EGVV` Swanwick Military, `EDXX` FIS only) не перекрывают FIR. Среди оставшихся выбирается большая (London TMA `EGTL` внутри `EGTT`). В Австралии у VATSpy только секторы (YGUN «Melbourne (Gundagai)»), станция там — по сектору.
3. Логон принимается в любой FIR. Реальное покрытие CPDLC (в Европе — только выше FL285 и т. п.) не моделируется.

**Реализация.** Ядро: `packages/core/src/atc/` (`cpdlc.ts` — пакеты и профиль, `fir.ts` — точка в полигоне, позывной и имя органа, `rops.ts` — станция). Опция ядра `rops: { enabled, standAside }`, выход `CoreOutput.listen` — позывные станций, которые транспорт опрашивает до первой отправки (станция ждёт логона). Входящие с `to` = станция `X…` идут в станцию, остальные — авиакомпании. Сообщения УВД не ждут интервала между telex. Данные: `packages/data-sources/src/vatspy.ts` (FIR вдоль маршрута, центры VATSIM по префиксам VATSpy, включая UIR). Приложение: настройка «Станция УВД ROPS» (по умолчанию выключена, нужны живые данные), строка ROPS в статусе, события в ленте. Прочие запросы CPDLC до T25 получают `MESSAGE NOT SUPPORTED BY THIS ATS UNIT` (фраза живых станций Hoppie). На стоянке (ON_BLOCK) станция шлёт `LOGOFF` подключённому самолёту и перестаёт опрашиваться.

#### T24 — ROPS: PDC по запросу, сквок по региональным правилам
Запрос PDC (DCL) от пилота, ответ в реальном формате (ARINC 623 / ED-85A, американский PDC — `[ПРОВЕРИТЬ]` образцы): ВПП, SID, начальная высота, частота вылета, ATIS, сквок. Сквок — по региональным правилам (ORCAM и аналоги), с банлистом: аварийные и специальные коды по ICAO Annex 10 Vol IV, Doc 4444 и региональным AIP (7500/7600/7700, 2000, 7000, 1200, 1000, 7400 и т. д. — полный список только из источников). Данные, которых нет в OFP (начальная высота, частота), — только из источника или как одобренное допущение.
**Готово, когда:** тесты банлиста и диапазонов по регионам на реальных примерах; PDC для 3+ регионов (EU, US, Азия) совпадает с реальными образцами по формату.

**Анализ (2026-10-09).** Подробно — `06`, «DCL/PDC» и «Таблицы сквоков». Запрос пилота в Hoppie — telex `REQUEST PREDEP CLEARANCE <позывной> <тип> TO <назн.> AT <вылет> STAND <x> ATIS <буква>` (FBW `DclMessage.ts`, TopSky «RCD»). Европа и Азия — ARINC 623 DCL (RCD → FSM → CLD → CDA/WILCO → FSM). Образцы: AIP Сингапура eSUP 2018/013, AIP Малайзии SUP 02/25 и реальные DCL, расшифрованные из эфира ACARS (EDDF 2022/2023, EFHK/EGLL/LSZH 2025, WSSS/VHHH/VTBS/RKSI 2023). Официального европейского AIP с образцом не нашлось, поэтому для Европы — реальные DCL и руководство TopSky. США — PDC через хост авиакомпании, без ответа пилота: поля по FAA JO 7110.113F, раскладка — реальный PDC Delta (KMSP, 2025-12-29). Таблицы сквоков: EUROCONTROL CAL v4.13, FAA JO 7110.66H (NBCAP), ICAO APAC eANP Vol II (Table ATM II-APAC-2). Реальные сквоки попадают в рассчитанные блоки: EFHK 0437, EGLL 3403/4622, EDDF 0122, LSZH 3016, KMSP 3631, KPHL 2747/1772, WSSS 2214, VHHH 5132, VTBS 0747, RKSI 7135.

**Решения пользователя (2026-10-09):**
1. Станция DCL — `X` + индекс аэропорта вылета (EDDF → XDDF), как у TopSky (станция DCL — индекс аэропорта). Опрашивается на земле до взлёта, пока обмен не закончен.
2. Европа, Азия и прочие регионы — ARINC 623 DCL пакетами `cpdlc` (на проводе — как у станций Hoppie: значения в `@…@`). США — PDC telex с той же станции, раскладка как у Delta: `PDC <рейс> <IATA> <IATA>` / `**** PREDEPARTURE  CLEARANCE ****` / `<позывной> DEPARTING <ICAO>  TRANSPONDER <код>` / `SKED DEP TIME <hhmm>   EQUIP  <тип>` / `FILED FLT LEVEL <эшелон>` / `-CLEARED AS FILED-` / маршрут / `CLEARED <SID> DEPARTURE <фикс> TRSN` / `CLB VIA SID` / `EXP <эшелон> 10 MIN AFT DP,DPFRQ <частота>` / `XPCT RWY <ВПП>`. Без «EXC MAINT …» (высота SID неизвестна) и без суффикса оборудования. Нет SID — `UNABLE REVERT TO VOICE`.
3. Сквок: EUR — CAL (строки назначения, гражданские, ENR; орган = префикс страны, аэропорт или FIR вылета; направление; protection и via по назначению и FIR маршрута; пул CCAMS). США — NBCAP (ARTCC = FIR аэропорта по VATSpy, внутренний рейс — назначение в том же ARTCC, сначала первичные блоки). APAC — блоки FIR (I/D), страна по VATSpy `[Countries]`, сноски-ограничения 11–16 не используются, Австралия и Новая Зеландия внутри страны — любой код, кроме международных блоков. Вне таблиц — случайный код. Коды на 00 и специальные коды (банлист) не выдаются никогда.
4. Код 1000 (Mode S) пока не назначается — только в банлисте. Правило Mode S (реальный DCL EDDF выдаёт `SQUAWK 1000`) — отдельная задача.
5. Таблицы лежат в репозитории как TS-данные со ссылкой на источник, редакцию и дату. NBCAP — public domain. Условия повторного использования CAL (EUROCONTROL) и eANP (© ICAO) `[ПРОВЕРИТЬ]` до публичного релиза (`08`, решение 9).

**Допущения (одобрены пользователем 2026-10-09):**
1. FSM «RCD RECEIVED» уходит сразу, CLD (и PDC в США) — через 60–180 с, детерминированно от seed. В AIP Сингапура и Малайзии сказано «в течение 5 минут».
2. Запрос принимается в любое время на земле до взлёта (в AIP Сингапура и Малайзии — не раньше чем за 20 мин до TOBT).
3. Если пилот не ответил WILCO за 5 мин, ничего не шлём: текста отмены в источниках нет.
4. Номер PDC — от seed, 001–999. Строки ADT/STARTUP не пишутся: данных нет. Начальной высоты нет: её нет в OFP.
5. NEXT FREQ (DCL) — живой DEL, затем GND VATSIM; иначе OurAirports `DEL`/`CLD`/`GND`; иначе строки нет. DPFRQ (США) — живой APP VATSIM, иначе OurAirports `DEP`/`APP`. OurAirports — данные сообщества (public domain), точность не гарантирована (у EDDF реальный DCL даёт 121.905, в OurAirports такой частоты нет).
6. Названия FIR таблицы APAC сопоставлены с FIR аэропортов по VATSpy.dat `[Airports]` (Китай: ZBPE и т. д.; Япония: ACC-области RJTG/RJBG/RJDG; Австралия: секторы VATSpy «Brisbane (…)» / «Melbourne (…)»).

**Реализация.** Ядро: `packages/core/src/atc/dcl.ts` (запрос, FSM/CLD/CDA, PDC США, отказы), `packages/core/src/atc/squawk/` (`squawk.ts` — выбор кода и банлист, `eur-cal.ts`, `faa-nbcap.ts`, `icao-apac.ts` — сгенерированные таблицы). Станция DCL работает внутри станции ROPS (настройка «Станция УВД ROPS»). Данные: страна и FIR вылета и назначения из VATSpy, частоты аэропорта вылета из OurAirports (`packages/data-sources/src/ourairports.ts`). В духе решения T23 «не конфликтовать с живыми диспетчерами»: если на VATSIM онлайн DEL/GND/TWR аэропорта вылета и включена настройка «Уступать», запрос отклоняется (FSM `RCD REJECTED / REVERT TO VOICE PROCEDURES`).

#### T25 — ROPS: запросы эшелона, скорости, Direct To, логика эшелонов
Ответы на запросы пилота: эшелон, скорость, Direct To — фразеологией CPDLC (CLIMB TO, UNABLE, DUE TO …). Логика эшелона: полукруговое правило и таблица крейсерских эшелонов (ICAO Annex 2, App. 3), RVSM FL290–410, исключения по государствам (AIP; метрические эшелоны — `[ПРОВЕРИТЬ]`), MORA/MEA сектора (из навлога SimBrief, если поле есть, `[ПРОВЕРИТЬ]`), потолок самолёта из OFP. Direct To — только на точку маршрута впереди. Отказ «из-за трафика» — допущение, только с одобрением.
**Готово, когда:** таблица эшелонов и исключений под тестами; нечётный эшелон в «чётной» зоне отклоняется с правильной причиной.

**Анализ (2026-10-09).**
- Запросы пилота (FBW A32NX `CpdlcMessageElements.ts`, GPL-3.0, только формат; в сети значения без `@`): DM6 `REQUEST <уровень>`, DM9 `REQUEST CLIMB TO <уровень>`, DM10 `REQUEST DESCEND TO <уровень>`, DM18 `REQUEST <скорость>`, DM22 `REQUEST DIRECT TO <точка>`. Уровень — `FL350`, `11000FT` или `8900M`; скорость — `M.78` (FANS-A: M.61–M.92) или `280` / `280KT` (70–350 kt). Ответы FANS-A: UM0 `UNABLE`, UM20 `CLIMB TO <уровень>`, UM23 `DESCEND TO <уровень>`, UM74 `PROCEED DIRECT TO <точка>`, UM106 `MAINTAIN <скорость>` (все WU, кроме UNABLE), UM169 — свободный текст (причины `DUE TO …`). В наборе FANS-A у FBW нет UM166/UM167 (`DUE TO TRAFFIC`, `DUE TO AIRSPACE RESTRICTION` — ATN B1, Doc 4444 Annex 5), их текст идёт как UM169.
- Таблица эшелонов: SERA, Appendix 3 (Рег. (ЕС) 923/2012; совпадает с ICAO Annex 2, App. 3, таблица a, футы, RVSM): 000–179° — FL10, 30 … 290, 310 … 410, 450, 490; 180–359° — FL20, 40 … 280, 300 … 400, 430, 470, 510. Путевой угол — магнитный.
- Исключения, сверенные с AIP: Испания (AIP ENR 1.7-3, AMDT 403/26 от 19-FEB-26) и Португалия (ENR 1.7.5, действует с 01 OCT 2026) — 090–269° нечётные, 270–089° чётные, та же сетка уровней. Франция — так же, но только для IFR в UTA (AIC A 06/20, с 21 мая 2020; таблица — AIP France ENR 1.3.5, `[ПРОВЕРИТЬ]` нижнюю границу UTA и сам текст ENR 1.3.5). Новая Зеландия (CAA NZ Part 91, ам. 12) — 270–089° нечётные, 090–269° чётные (зеркально Испании). Италия — то же, что Испания, по документу ENAV о Free Route выше FL335; текст ENR 1.7 Италии не получен — `[ПРОВЕРИТЬ]`.
- Метрические эшелоны (Китай, КНДР; Монголия и страны СНГ — по разным годам переходили на футы): официальные таблицы AIP не получены, есть только вторичные источники и рабочий документ ICAO A36-WP/176 (китайско-российская таблица RVSM в метрах) — `[ПРОВЕРИТЬ]`.
- SimBrief: в каждой точке навлога есть `mora` (ft), `fir`, `fir_units`, `fir_valid_levels` (допустимые эшелоны плеча с учётом направления и ограничений трассы: на M750 в RJJJ — от FL270), `fir_crossing`, `track_mag`. В `general` — `stepclimb_string` (`RCTP/0390` = точка/эшелон в сотнях футов; формат нескольких ступеней `[ПРОВЕРИТЬ]` на OFP со step climb). Потолка самолёта в OFP нет (в `aircraft` только тип, двигатели, оборудование). Признак RVSM — буква `W` в `aircraft.equip` (поле 10a FPL, Doc 4444, App. 2).
- Телеметрия даёт IAS, но не Mach и не магнитный курс: магнитный путевой угол берётся из `track_mag` текущего плеча навлога.
- Потолок и VMO/MMO — EASA TCDS (сверено 2026-10-09): A.064 A318–A321 iss. 62 (39 800 ft с мод. 30748, VMO 350 kt / MMO 0,82), A.004 A330 iss. 69 (41 450 ft), A.151 A350 iss. 33 (-900 43 100 ft, -1000 41 450 ft), IM.A.120 B737 iss. 29 (NG и MAX 41 000 ft), IM.A.003 B777 iss. 20.0 (43 100 ft), IM.A.115 B787 iss. 30 (-8/-9 43 100 ft, -10 41 100 ft, VMO 350 / MMO 0,90), IM.A.196 B747 iss. 19 (-400 45 100 ft, -8 43 100 ft, VMO 365 / MMO 0,90). A.110 A380 iss. 17 — «см. AFM», чисел нет.

**Решения пользователя (2026-10-09):**
1. Допустимые эшелоны: чётность — своя таблица (SERA App. 3 и исключения ES/PT/FR-UTA/NZ, остальные FIR — по ICAO); ограничения трассы — `fir_valid_levels` SimBrief, когда самолёт на плече навлога (если пересечение со своей таблицей пустое — только своя таблица).
2. Метрические районы (Китай, КНДР) — футовая таблица ICAO (допущение: в Китае реальные эшелоны метрические).
3. Отказ «из-за трафика» (`UNABLE@_@DUE TO TRAFFIC`) — 10 % допустимых запросов эшелона, от seed, не два раза подряд; повтор того же запроса через 5+ мин одобряется.

**Допущения (одобрены пользователем 2026-10-09):**
1. Потолок и VMO/MMO — из TCDS (список выше; у A318–A321 — 39 800 ft, самая распространённая модификация 30748). Тип без данных — без проверки. Потолок по массе не моделируется. Ниже FL100 скорость > 250 kt отклоняется везде (14 CFR 91.117; в SERA — не во всех классах).
2. Direct To — только на точку маршрута впереди, в текущем FIR, не дальше первой точки STAR; иначе `UNABLE`.
3. Ответ — через 20–60 с от seed. Самолёт без `W` в оборудовании — `UNABLE` на FL290–410.
4. Ниже MORA текущего плеча — `UNABLE` без причины.
5. Италия — по ICAO, пока текст AIP Италии ENR 1.7 не получен (`[ПРОВЕРИТЬ]`). Франция — исключение выше FL195 (нижняя граница UTA `[ПРОВЕРИТЬ]`). Новая Зеландия — только FIR NZZC.

**Реализация.** Ядро: `packages/core/src/atc/requests.ts` (разбор запросов и решение), `levels.ts` (таблица и правила государств), `performance.ts` (TCDS), `route.ts` (плечо маршрута, точка входа в STAR). OFP: `OfpFix.trackMag/moraFt/fir/validLevelsFt`, `OfpAircraft.equip`. Станция ROPS отвечает только станции, на которую самолёт залогинен (иначе, как раньше, `MESSAGE NOT SUPPORTED`); решение принимается при получении, ответ — через 20–60 с (очередь в `RopsState.req`, переживает сохранение состояния). Событие `ATC_REQUEST` — в ленте приложения и отчёте replay. Если телеметрии нет — `UNABLE`. Магнитный путевой угол — из `track_mag` плеча, на котором самолёт; плечо без `track_mag` — без проверки чётности.

#### T26 — ROPS: случайные Direct To, step climb, начальная высота снижения
До 3 случайных Direct To за полёт (seeded Rng, только точки впереди по маршруту, реалистичные ограничения — `[ПРОВЕРИТЬ]`). Автоматическое разрешение step climb по ступеням OFP (событие `ALT_CHANGE`, поле ступеней в OFP `[ПРОВЕРИТЬ]`). Разрешение на снижение с логичной начальной высотой вместо общего «descend via STAR»: по маршруту, фазе, MORA, эшелону перехода назначения. Алгоритм выбора высоты согласовывается как допущение.
**Проверка человеком:** сообщения приходят вовремя в Fenix/FBW/PMDG, принимаются CPDLC-страницей.

**Анализ (2026-10-09).** Оригинал (`01`): клиренс на снижение — за ≤ 20 NM до TOD, step climb — при пересечении 23500/28500 ft, оба через сервер автора. У нас — станция ROPS ядра (T23), фразы FANS-A из T25 (`PROCEED DIRECT TO`, `CLIMB TO`, `DESCEND TO`; FBW также знает `WHEN ABLE PROCEED DIRECT TO`, `AT PILOTS DISCRETION`). Ступени — `general.stepclimb_string` и смены `altitude_feet` в навлоге на этапе `CRZ`. Для начальной высоты снижения есть `mora` по точкам, `transLevelFt` назначения, высоты навлога на этапе `DSC` (профиль SimBrief, не ограничения STAR). Реальных ограничений на случайные Direct To в источниках нет: выбор точек — допущение.

**Допущения (одобрены пользователем 2026-10-09):**
1. Случайные Direct To: 0–3 за полёт от seed; только в крейсере и не ближе 50 NM до TOD; точка в текущем FIR, на 50–250 NM впереди, не SID/STAR, спрямление ≥ 2 NM; `PROCEED DIRECT TO @X@` (WU).
2. Step climb: за 2 мин до точки ступени — `CLIMB TO @FLxxx@` (WU); не шлём, если пилот уже запросил этот эшелон или эшелон не подходит по таблице T25.
3. Снижение: за 20 NM до TOD (как у оригинала). Начальная высота — наибольшая из: высота навлога SimBrief у первой точки STAR; MORA оставшегося маршрута + 1000 ft; округление вверх до 1000 ft. Выше эшелона перехода назначения — `DESCEND TO @FL120@`, ниже — `DESCEND TO @6000FT@`.

**Реализация.** Ядро: `packages/core/src/atc/auto.ts` (точки случайных Direct To, выбор точки, ступени, высота снижения), вызов — `RopsStation.autoClearances` (только залогиненному самолёту с телеметрией, фазы CRUISE/DESCENT; состояние — `RopsState.auto`). OFP: `Ofp.stepClimbs` из `general.stepclimb_string` (`FIX/0410`, первая пара — аэропорт вылета). Точки Direct To — 0–3 случайных расстояния по маршруту в [TOC, TOD − 50 NM], при их прохождении выбирается точка по правилам; если подходящей нет, Direct To не будет. Точки, пройденные больше чем на 30 NM (старт посреди полёта), отбрасываются. Ступень, пройденная больше чем на 20 NM, отбрасывается. Снижение не шлётся, если уже разрешён более низкий уровень или вычисленный уровень не ниже текущей высоты на 1000 ft. Если у назначения нет ни эшелона, ни высоты перехода, граница FL/футы — 18 000 ft (`[ПРОВЕРИТЬ]`, не согласовано). Событие `ATC_AUTO` — в ленте и отчёте replay.

**Решение пользователя (2026-10-09):** случайные Direct To включаются и выключаются: опция ядра `rops.randomDirects` (по умолчанию включена, пишется в заголовок записи полёта), в приложении — настройка «Случайные Direct To». Step climb и снижение от неё не зависят.

#### T27 — ROPS: океанический клиренс
Запрос и выдача океанического клиренса, если маршрут входит в океанический район (NAT, PACOTS и т. п.). Формат — по реальным образцам (Shanwick/Gander/New York, data-link OCL `[ПРОВЕРИТЬ]`). Трек, точка входа, время, эшелон, Mach — из OFP и актуальных треков (источник `[ПРОВЕРИТЬ]`). Окно запроса — по правилам района `[ПРОВЕРИТЬ]`.

#### T28 — Пуски ракет рядом с маршрутом
Адаптер TheSpaceDevs Launch Library (версия и лимиты `[ПРОВЕРИТЬ]`, кэш обязателен), сценарий в `external/`: пуск в пределах 300 NM от маршрута и в окне времени полёта. Только реальные данные; нет пуска — нет сообщения. Данные пишутся в запись полёта.
**Готово, когда:** фикстура реального ответа, тест расстояния и окна, деградация без сети.

#### T29 — Special Events (результаты спортивных матчей и т. п.)
Сообщения о реальных событиях (например, результаты крупных футбольных матчей). Источник — API с документированными условиями использования (`[ПРОВЕРИТЬ]` лицензию и нужен ли ключ). Ключ — только ввод пользователем или бэкенд (инвариант 2). Факты только из API.

#### T30 — CONNEX schedule: стыковочные рейсы авиакомпании
Перед прилётом — список реальных стыковочных рейсов той же авиакомпании (и партнёров — `[ПРОВЕРИТЬ]`) из пункта назначения: рейс, направление, время, гейт, если есть. Источник расписаний — `[ПРОВЕРИТЬ]` (что использовал оригинал — по `01`; платные API — ключ у пользователя или на бэкенде). Нет данных — нет сообщения.

### Приоритет 2

#### T31 — Имитация линии передачи: VHF, спутники, SATCOM, задержка
Ядро выбирает наземную VHF-станцию в прямой видимости или (при SATCOM в профиле самолёта) спутник и задаёт задержку доставки. База VHF-станций — из проверяемых источников (`[ПРОВЕРИТЬ]`: открытого авторитетного списка SITA/ARINC может не быть — тогда только с одобрением). Спутники: Inmarsat (GEO), Iridium (TLE CelesTrak + SGP4, лицензия библиотеки `[ПРОВЕРИТЬ]`). Задержки — по реальным данным. TLE и база — в записи полёта.

#### T32 — Заголовки AES/GES и окно состояния линии
Динамический заголовок по реальным образцам (`AES:… GES:… .<рег>`), ICAO hex борта (ввод в профиле или источник `[ПРОВЕРИТЬ]`), правило переноса для узких дисплеев. Окно в приложении: станция или спутник, время передачи. Зависит от T31.

#### T33 — Пожар у аэропорта назначения
Нестандартный сценарий: пожар рядом с ВПП, влияние на видимость, рекомендация подготовить диверсию, продолжение через ~20 мин. Условия (ВПП из OFP/METAR, ветер) — реальные.

#### T34 — Эффекты в симуляторе: столб дыма с учётом ветра
По T33 мост создаёт объект с эффектом дыма у ВПП (SimConnect, пакет для Community). Ветер — из симулятора. Влияние на производительность ограничено. Зависит от T21, T33.
**Проверка человеком:** MSFS 2024, сценарий T33: дым виден издалека, сносится по ветру, FPS не падает заметно.

#### T35 — Редактор своих сообщений
UI: условие отправки (триггеры движка) и перетаскивание полей данных (`ofp.*`, `wx.*`, `ext.*`) → YAML с валидацией по схеме, через форматтер. Основа — T20.

#### T36 — CTAF в сообщении VATSIM
Для аэропортов США без онлайн-диспетчера — CTAF из источника частот (FAA NASR или OurAirports, лицензия и дата сверки `[ПРОВЕРИТЬ]`).

#### T37 — Funny messages
Набор юмористических сценариев с малой вероятностью. Без реальных людей, без оскорблений, не в критических фазах (sterile cockpit).
